# 计划文档闭环审计与清理

> 适用：用户说「把计划/指南/清单类文档验证一遍，闭环了就删掉」。
> 核心风险：**文档里写着 ✅ 不等于代码里做了；删了文档就等于销毁证据。**

## 0. 先读
`policy.md` §5（文档纪律）· `.agent/memory/known-issues.md` · `CLAUDE.md` §6。
**先看历史**：本项目 `计划书/` 9 个文件在 v9.2.0 以「全部闭环」为由删除，
2026-10-16 独立复验推翻了该理由（至少 6 项部分闭环、3 项零生产调用点）。**不要重犯。**

## 1. 枚举候选（只读）
```bash
find . -name "*.md" -not -path "./.venv/*" -not -path "./.git/*" \
  -not -path "./build/*" -not -path "./dist/*" | sort
```
按文件名/首段判断类型：

| 类型 | 例 | 处置 |
|------|----|------|
| 计划 / 改进指南 / 待办 | `下一步改进指南.md` | 审计 → 归档 → 删除 |
| 验收清单 / 规划总览 | `计划书/*.md` | 审计 → 归档 → 删除 |
| **活文档**（每次发版都用的 SOP） | `docs/RELEASE_CHECKLIST.md` | **保留**（这是流程，不是计划） |
| 事实源（架构/契约/数据模型/ADR） | `docs/architecture.md` 等 | **保留** |
| 历史证据（验证记录/审计快照） | `docs/验证记录-*.md`、`docs/reports/*.html` | **保留**（只读快照，不改数字） |
| 指针墓碑（目录已清空的 README） | `计划书/README.md` | 可归档后删除，**先查死链** |

## 2. 逐条建台账
每条任务提取：`ID · 原文 · 所属文档/章节 · 类型 · 声称状态 · 证据 · 实际状态`。

**实际状态只看三样东西**（按可信度排序）：
1. 代码里的**生产调用点**（不是测试引用）——`grep -rn "<symbol>" gcm/`
2. UI 入口（控件 → 保存回调 → 消费方，三段都要通）
3. 本轮真实运行输出

分类：`已闭环 / 部分闭环 / 伪闭环（声称有但零实现）/ 未闭环 / 需用户决策 / 已过时 / 不适用`。
**「伪闭环」与「未闭环」都算未完成，不得因文档写 ✅ 而放行。**

## 3. 常见伪闭环形态（本项目高频）
- 后端模块 + 单测齐全，**设置页无控件** → 用户不可达
- 信号 emit 了但**没 connect**；构造函数回调参数**恒为 None**
- 设置了字段但**没有消费方**（只写不读 / 只读不写）
- 函数定义在 `theme.py`/`app/*.py`，**生产零调用**（只在 tests 出现）
- 台账把「派生视图已有」写成「列/图已实现」

## 4. 处置未闭环项
- 能安全修的 → 修 + 补守卫 + 验证。
- 需 DB 迁移 / 产品决策 / 新增外部依赖 → **保留文档**，登记到 `CLAUDE.md` §6 与
  `.agent/memory/known-issues.md`，标注「需立项」。
- 需求本身已撤销（如模块因零调用被删）→ 标 `不适用/已过时`，写清撤销依据。

## 5. 归档（删除前必做）
```bash
mkdir -p docs/archive/plans/YYYYMMDD
git mv <doc> docs/archive/plans/YYYYMMDD/
```
在归档目录写 `archive-manifest.md`：原路径 · 归档时间 · 提交 · 审计结论 ·
逐条状态表 · 仍开放的项指向何处 · 恢复方法（`git show <sha>:<path>`）。

**删除的四个前提（缺一不可）**：
1. 已完成逐条审计并有报告；
2. 原文档已进入归档目录；
3. 已列删除清单并核对；
4. 文档内**没有**未闭环 / 需用户决策的项（有则保留）。

## 6. 删后必查死链
```bash
grep -rn "<被删路径>" --include="*.md" --include="*.py" --include="*.yml" .
python -m unittest tests.test_g67_docs_freshness
```
**历史提示（已过期，勿据此改动守卫）**：早先 `tests/test_g67_docs_freshness.py` 的
`_PATH_PREFIXES` 曾含 `计划书`；现在该列表是
`("gcm", "docs", "scripts", "skills", "tests", "packaging", "evidence")` ——
`计划书` 属于 `docs` 之下，删除该目录**不需要**改守卫。实测口径：删目录后跑一遍
`python -m unittest tests.test_g67_docs_freshness` 即可，红了再改文档。

## 7. 验收输出
审计表（每条任务的六列）· 删除清单 · 归档 manifest 路径 · 死链检查结果 ·
仍未闭环项的去处 · 本次实际运行的命令与输出。

## 常见坑
- 把「活 SOP」当计划删掉（`RELEASE_CHECKLIST.md` 是每次发版要用的）。
- 只 grep 文件名而不 grep 内容，漏掉正文里的相对路径引用。
- 删除后用「文档已删」当完成证据 —— 这正是 2026-10-16 复验推翻的说法。

## 2. 设计口径（Design Before Code）

### 2.1 本专项的宪法：三条

1. **可用性改进不得制造可用性缺陷。**
   实测教训：撤销浮条最初用绝对定位盖在中央控件底部，把下载页整排按钮
   （打开克隆目录 / 失败汇总 / 重试队列 / 诊断包）挡住 —— 加撤销反而少了 4 个按钮。
   现在它**进布局**、隐藏不占位、显示时自己占一行（`overlaps: 0` 有守卫）。
2. **单一事实源优先于方便。**
   快捷键表、撤销可用性判定、错误可重试判定，都只能有一处定义。
   本轮把帮助页的快捷键表改成**从 `ui/menu_bar.SHORTCUTS` 派生**，从根上消灭漂移。
3. **不可撤销的操作，必须让用户事前看见后果。**
   确认框与撤销是**两条腿**：确认框防「手滑」，撤销救「想错了」。
   凡承诺可撤销的，必须有真的逆做实现；做不到就 `undoable=0` 且 UI **不得**画撤销按钮。

### 2.2 撤销的分层（D-2 的落地口径）

| 层 | 职责 | 文件 | 为什么这样切 |
|----|------|------|------------|
| 记录层 | 只记「发生了什么 + 旧值快照」，不知道任何业务 | `util/oplog.py` | 可原样给 CLI / MCP 复用（只读查看历史），不牵扯 db |
| 分派层 | 只做逆做，不知道文件格式 | `app/undo.py` | 逆做要调 `owner.db` 写方法，只有 UI 主进程持有完整上下文 |
| 入口层 | 浮条 / 操作历史 / 菜单项 | `ui/undo_bar.py` + `ui/menu_bar.py` | 遵守「新增 UI 逻辑一律落独立模块」 |

**为什么不用数据库表（Rev10 O-01 方案）**：那需要 `_SCHEMA_VERSION` 8→9 迁移，
是 `policy.md` 的 **T3 高风险**（持久化数据），且 Rev10 尚未开工。本方案用独立 JSON，
代价是少一次 JOIN，收益是**零迁移、零回滚方案、可整体删除**。详见 `util/oplog.py` 模块文档。

**三个不变量**（破坏任一条都会让「撤销」变成新的数据丢失源）：

1. **单写者**：读-改-写在**同一个** `cross_process_lock` 临界区内（照抄
   `db/progress_file.py:68-93` 的范式 —— 那条注释记录了当年"load 取锁又释放、
   save 再独立取锁"导致丢更新的教训）。有并发测试：20 线程写 20 条，一条不丢。
2. **出站即打码**：`before_json` 可能出现 `https://user:pass@host`，**落盘前**过 `redact()`
   （不是展示层才打码 —— 诊断包会整个搬走这个文件）。有测试断言明文 token 不在文件里。
3. **`undoable` 是承诺**：`1` = 有真逆做；`0` = 只记录，UI 不得画撤销按钮。
   `can_undo()` 是唯一判据，UI 不许自己判断。

### 2.3 可撤销操作分级（照此新增，不要临时决定）

| 操作 | `undoable` | 逆做方式 | 理由 |
|------|-----------|---------|------|
| 删除仓库记录（含批量） | **1** | `upsert_repo` + 单独恢复 tags/favorite/excluded | 纯 DB 行，快照可完整重建 |
| 清空重试队列 | **1** | `restore_entries()`（与 `clear()` 对称） | 丢的是「即将自动重试」的任务，代价最高 |
| 清空地址历史 | **1** | 倒序 `add()`（`add` 是头插） | 轻量但用户手打成本高 |
| 清空输入区 | **1** | 追加写回 | 常是手打的几百行地址 |
| 删除清单 | **1** | `TaskLists.save()` | 有原文即可重建 |
| 修改标签 / 收藏 / 排除 | **1**（已登记） | `set_tags` / `set_favorite` / `set_excluded` | 逆做简单，待接入记录点 |
| `prune_history` / 批次克隆 / 删除半成品目录 | **0** | — | 动磁盘或经设计为不可逆；**只能靠确认框**，不得画撤销按钮 |

> **禁止**：为了"看起来更完整"把 `undoable=0` 的操作标成 1。那是伪闭环，
> 用户点了撤销却什么也没恢复，比没有撤销按钮更伤信任。

### 2.4 反馈的三档（治 U-15 的口径）

| 档 | 何时用 | 形态 | 时长 |
|----|--------|------|------|
| **即时** | 点击后 < 100ms 内可有结果 | 状态栏 `showMessage` | 3–5s |
| **浮条** | 操作已完成、且**可撤销** | `UndoBar`（不抢焦点） | 5s，成功后 1.5s |
| **忙态** | 操作 > 1s 且不可撤销 | `busy()` 禁用按钮 + 事件总线 | 至完成 |

**禁止**：为「值得开心」的事弹模态框。模态框打断当前动作，用户会条件反射点掉它 ——
撤销就失效了（这也是撤销必须做成浮条而非对话框的原因）。

### 3.1 主窗菜单栏（D-3）

```
文件(F)   编辑(E)   视图(V)   工具(T)   帮助(H)
```

| 菜单 | 项 | 说明 |
|------|----|------|

| 编辑 | 3 项 | **撤销(Ctrl+Z)**、**操作历史…**、清空输入区 |
| 视图 | 6 项 | 切三页签、放大/缩小/复位字号 |
| 工具 | 7 项 | 命令面板、失败汇总、重试队列、后台任务、统计中心、诊断包、自检 |
| 帮助 | 4 项 | **使用说明(F1)**、开始使用清单、检查更新、关于 |

**实测：27 项，0 项灰置**（`已验证`）。每项都绑到主窗真实公开方法；
目标方法缺失时 `_act()` 会置灰并给 tooltip，而不是生成"点了没反应"的假菜单项。

### 3.2 撤销浮条的形态

- **位置**：`tabs` 与状态栏之间的布局行（**不是**覆盖层）。
- **隐藏态**：不占高度（显示浮条时 `tabs` 高度实测 631→573）。
- **外观**：`panel_primary` 底 + `border_strong` 描边 + `cta` 主按钮。
  **不用 accent** —— accent 的语义是「正在发生」（进度/焦点/活跃页签），
  撤销浮条是「刚刚发生、还可回退」，抢用会让色彩预算通胀（守卫按色值计数，实测会红）。

### 3.3 帮助的形态

- 入口：`帮助 → 使用说明` 与 `F1`（同一个槽，防漂移）。
- 快捷键表：**从 `ui/menu_bar.SHORTCUTS` 派生**，不再手写。
- 有守卫：帮助页必须覆盖 `SHORTCUTS` 里每一条（漏一条即红）。

## 9. 残留决策（执行到对应项时必须先问）

| # | 决策点 | 为什么要问 |
|---|--------|-----------|

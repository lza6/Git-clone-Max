# Git-clone-Max 下一步改进指南（v1.1.0 → v2.0 迭代路线图）

> 文档定位：本项目**唯一权威**的迭代升级计划书，供任意 AI 开发者按此实施。
> 当前基线版本：**v1.1.0**（已发布 Release，exe 已上传 GitHub，全链路 E2E 通过）。
> 本文档按「**P0 必修 → P1 重要 → P2 增强 → P3 远期**」四级编排，先做能立刻止血的，再做提升体验的，最后做突破性的。每一条都有验收标准，杜绝"假实现"。

## 一、项目现状与基线（审计结论）

### 1.1 技术栈

| 项 | 值 |
|----|----|
| 语言 / 运行时 | Python 3.14（Windows py launcher），无 mypy/ruff 强制 |
| GUI | PyQt6（QThreadPool + QRunnable 并行 worker） |
| 数据库 | SQLite（WAL）+ `progress.json` 原子断点续传 |
| Git | 调系统 git CLI：clone / fetch --prune / merge --ff-only / rebase 回退 |
| 打包 | PyInstaller `--onefile --windowed`，94MB 单文件 |
| 测试 | unittest，13 核心 + 1 启动器，真实裸仓库 E2E |
| 发布 | GitHub Releases + PyGithub 上传（已踩过 multipart 的坑，脚本在 `scripts/publish_release.py`）|

### 1.2 已实现功能清单（基线）

1. 批量并行（≤8 线程）clone / 增量更新，互不阻塞
2. `作者__仓库` 目录命名（防重名）
3. 增量更新：fetch → 冲突检测 → merge --ff-only → rebase 回退 → 冲突保留本地
4. 半成品目录自动清理重克隆
5. SQLite 记录仓库 + 同步历史快照（`repos` / `sync_history` 两张表）
6. `progress.json` 原子断点续传（temp + os.replace）
7. 一键更新全部 + 管理 Tab 增删查
8. 深色 GitHub 风 UI：三 Tab、实时日志、关键字高亮、导出
9. bat/ps1 启动器：自动建 venv、装依赖、检测 git/python
10. 下载完成自动清空输入框
11. 单文件 exe（双击即用）+ 正式 Release v1.1.0

## 二、改进路线图（按优先级）

### P0 — 必修：可靠性与可用性止血（第一优先级）

> 这组改动直接影响"用户会不会炸"，优先级最高，必须先做。

#### P0-1 输入校验不静默丢行（修 A2）

- **改动文件**：`gcm/ui/main_window.py`
- **方案**：解析前逐行校验，非法行（空行除外）高亮列出并弹窗提示"以下 N 行无效：…"，用户可选"忽略并继续"或"返回修改"；有效行才进入任务。
- **验收**：粘贴 3 有效 + 1 无效地址，点开始 → 弹窗列出无效行；忽略后仅 3 个任务入表。

#### P0-2 全局超时 + HTTP 代理支持（修 A6）

- **改动文件**：`gcm/git/service.py`、`gcm/ui/main_window.py`（设置 Tab）
- **方案**：
  1. `GitService` 增加 `fetch_timeout` / `clone_timeout`（默认 300s，可配置）；超时 `terminate` 并标记 FAILED("超时")。
  2. 设置 Tab 增加代理输入（`http_proxy` / `https_proxy`），写入 `git -c http.proxy=...` 环境变量传入 subprocess。
- **验收**：设 `timeout=0.001` 跑真实 fetch → 返回 FAILED + "超时"，无残留 git 进程；设代理指向本地无响应端口 → 任务失败且不挂死。

#### P0-3 进程树彻底取消（修 A3）

- **改动文件**：`gcm/git/service.py`
- **方案**：`run_git_ui` 增加 `group=True`，Windows 用 `creationflags=CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`，取消时 `proc.terminate()` 失败则 `taskkill /PID <pid> /T /F`；`cancelled()` 每行回调。
- **验收**：启动长 clone → 点取消 → `tasklist` 中无残留 git.exe；`cancel_all` 后所有行标记"已取消"。

#### P0-4 崩溃自愈：启动自检 + 残留清理

- **改动文件**：`gcm/__main__.py`
- **方案**：启动时检查 `data/clones` 下无 `.git` 的半成品目录（写入 `*.gcm-tmp` 标记），弹窗确认后删除重建；`progress.json` 损坏自动重置。
- **验收**：手工造一个假半成品目录 → 启动 → 弹窗提示清理。

### P1 — 重要：体验与工程化完善（第二优先级）

#### P1-1 断网自动重试（修 A7）

- **改动文件**：`gcm/git/service.py`
- **方案**：clone/fetch 失败时按 `(1s, 3s, 8s)` 退避重试 2 次；连续失败才 FAILED，并区分"网络错误（超时/无法连接）"与"仓库错误（404/认证失败）"文案。
- **验收**：单测 mock 前 2 次失败第 3 次成功 → 返回 SUCCESS；3 次全失败 → FAILED 且 detail 含"网络错误"。

#### P1-2 配置持久化（修 A10）

- **改动文件**：新增 `gcm/db/settings.py`；`gcm/__main__.py`、`gcm/ui/main_window.py`
- **方案**：`settings.json`（存于 data 目录）保存：并发数、浅克隆默认、深度、自动清空开关、代理、日志导出路径。`Settings` 类封装 load/save（原子写，同 progress.json）。
- **验收**：改并发=4 → 重启 → 仍为 4；单测覆盖 load/save/损坏兜底。

#### P1-3 并发数动态可调 + 不再共享全局池（修 A3）

- **改动文件**：`main_window.py`
- **方案**：每个窗口自建 `QThreadPool`（`setMaxThreadCount` 来自设置），不碰 `globalInstance()`；设置 Tab 加"并发数" SpinBox（1–16），运行中调低仅对新任务生效。
- **验收**：并发 16 起 16 个任务全并发；并发 1 串行；UI 上并发数即时显示。

#### P1-4 发布脚本固化 + 依赖声明（修 A8）

- **改动文件**：`requirements.txt`、`scripts/publish_release.py`、新增 `requirements-build.txt`
- **方案**：`requirements.txt` 加 `PyGithub>=2.0`；新建 `requirements-build.txt`（PyInstaller + PyGithub）；发布脚本支持 `--dry-run`（校验本地 exe 存在、sha256 与远端一致）与 `--tag` 参数，从 tag 自动生成 Release body（读取 CHANGELOG 段落）。
- **验收**：`python scripts/publish_release.py --dry-run` 本地通过；产物列表带 sha256 校验行。

#### P1-5 UI 自动化测试（修 A9）

- **改动文件**：新增 `tests/test_ui.py`；`tests/test_launcher.py`
- **方案**：用 `QT_QPA_PLATFORM=offscreen` + QtTest 驱动：输入非法行弹窗、合法行入表、`_launch` 后按钮禁用/恢复、清空输入框触发。覆盖主流程关键槽函数。
- **验收**：`python -m unittest discover -s tests -v` 全绿，新增 ≥8 个 UI 用例。

#### P1-6 冲突检测统一语义（修 A1）

- **改动文件**：`gcm/git/service.py`
- **方案**：重写 `_branch_ahead` 为「本地领先上游数」（`@{upstream}..HEAD`），删除冗余函数，统一一个 `_divergence_info` 返回 `(ahead, behind)`；`_detect_conflict` 依赖它。
- **验收**：单测：本地领先+远端领先 → conflict；仅远端领先 → 可快进；干净 → fetched。

### P2 — 增强：体验与健壮性上台阶（第三优先级）

#### P2-1 空仓库/无 HEAD 优雅处理（修 A4）

- **改动文件**：`service.py`、`worker.py`、`main_window.py`
- **方案**：clone 后 `_head_sha` 为空 → 状态 SUCCESS + action `EMPTY_REPO`（新枚举），DB 记录空 HEAD，UI 显示"空仓库（暂无提交）"徽标；设置 Tab 增加"空仓库自动初始化 main 并推送"开关。
- **验收**：真实建一个空裸仓库 → clone → 显示空仓库状态；开启自动初始化后有初始 commit。

#### P2-2 日志架构优化：单缓冲 + 分仓库过滤（修 A5）

- **改动文件**：`theme.py`、`main_window.py`
- **方案**：日志 Tab 加「过滤仓库」下拉（全部/按 owner__repo）+ 级别过滤（全部/INFO/WARN/ERROR）；`LogModel` 增加按条件快照，`log_view` 渲染逻辑抽为函数，避免每次全量重绘。
- **验收**：1000 条日志下切换过滤即时；内存占用相比改前不增反降。

#### P2-3 一键更新根目录自适应（修 A12）

- **改动文件**：`main_window.py`
- **方案**：数据库 `local_path` 反推根目录集合（`set(path.parent)`），逐个根目录发起任务，任务头带所属根目录标签；跨目录不再漏。
- **验收**：建两个不同根目录的仓库记录 → 一键更新 → 两个目录都被正确更新。

#### P2-4 自更新（修 A13）

- **改动文件**：新增 `gcm/app/updater.py`；设置 Tab 增加"检查更新"
- **方案**：`GET /repos/lza6/Git-clone-Max/releases/latest`，比对 `__version__`（`gcm/__init__.py`），发现新版弹窗给出下载链接；不做自动覆盖（防杀软/权限坑）。
- **验收**：mock 返回高版本 → 弹窗提示；同版本 → "已是最新"。

#### P2-5 系统托盘挂机（修 A14）

- **改动文件**：新增 `gcm/ui/tray.py`；`main_window.py`
- **方案**：`QSystemTrayIcon` 提供：显示/隐藏、进度摘要（成功/失败数）、"全部完成"通知；最小化到托盘可选。
- **验收**：托盘图标出现；任务完成弹出系统通知；点击托盘恢复窗口。

#### P2-6 打包体积与启动优化

- **改动文件**：`Git-clone-Max.spec`、新增 `build_icon.py`
- **方案**：exe 内嵌图标（ICO）；`--onefile` 保持但压缩 EXE 资源段；`--collect-all PyQt6` 仅收用到的模块（`QtWidgets/QtCore/QtGui/QtSvg`），可再减 10–20MB。
- **验收**：重新打包成功，体积下降，双击可跑（离屏冒烟 RC=124）。

#### P2-7 仓库详情页（衍生扩展）

- **改动文件**：新增 `gcm/ui/repo_detail_dialog.py`
- **方案**：管理 Tab 双击行 → 详情对话框：完整 HEAD、默认分支、最近 20 条同步历史表格（含 duration）、"打开目录/打开远端/删除"按钮。
- **验收**：双击任意行弹出详情，按钮各司其职。

### P3 — 远期：突破与生态（视版本规划）

- **P3-1 多平台**：`host` 字段已留位，扩展 gitlab/gitee/bitbucket 解析（url_lib 正则按 host 分流），Readme 表多平台。验收：gitlab URL 能正确解析并命名。
- **P3-2 CI 自动发布**（修 A15）：GitHub Actions `on: push tags` → 构建 exe → 自动创建 Release（直接复用 publish_release.py 的 PyGithub 逻辑）。
- **P3-3 私有仓库 / token 认证**（修 A16）：设置 Tab 存 GitHub token（`credential.helper` 已有 git 原生支持），clone 时注入 `-c credential.helper=...`。
- **P3-4 工作区并发（git worktree）**：大仓库支持多分支并行检出，按分支 clone，满足"同一仓库多分支同时要"的场景。
- **P3-5 多任务队列与调度**：加入队列优先级（拖动排序）、限速（KB/s）、仅局域网模式；断点续传升级为「多文件校验清单」。
- **P3-6 国际化**：UI 文案抽 `i18n.py`，至少 en/zh 两套。
- **P3-7 遥测与统计**：`sync_history` 聚合看板：仓库活跃度、失败率、Top 更新频率（只读分析，不上传任何数据）。

## 三、实施顺序建议（依赖关系与里程碑）

```
里程碑 M1（可靠性，第 1 周）＝ P0-1 + P0-2 + P0-3 + P0-4
里程碑 M2（体验，第 2 周）＝ P1-1 ~ P1-6（P1-2/P1-3 依赖 P0-2 的设置框架，先做）
里程碑 M3（进阶，第 3 周）＝ P2-1 ~ P2-7
里程碑 M4（远期，按需）＝ P3-x
```

依赖关系：
- `P1-3 并发可调` 依赖 `P0-3`（自建池 + 进程组）与 `P1-2`（设置持久化）。
- `P1-5 UI 测试` 依赖 P0/P1 的 UI 改动完成后写，避免测试打不稳定的桩。
- `P2-4 自更新` 依赖版本管理：当前 `gcm/__init__.py` 有 `__version__ = "1.0.0"`，但已发布 Release 为 `v1.1.0`——**不一致**，实施时需先统一为与最新发布一致的版本号（如 `2.0.0`）。
- `P2-6 打包` 应在所有 P0-P2 代码稳定后再打，否则白打。

**每完成一个里程碑都必须：** 全量跑测试套件（`python -m unittest discover -s tests -v`）+ 离屏冒烟（`QT_QPA_PLATFORM=offscreen` 起窗口）+ 如改动发布相关再重打包 exe。

## 五、改造约束与禁忌（防止实施跑偏）

1. **禁止大范围重构**：只做增量修改，保持既有文件结构与命名风格（`gcm/` 包内小步迭代）。
2. **禁止造轮子**：已有 `progress.json` 原子写、`QThreadPool` worker、`parse_repo_url` 等轮子直接复用/小改，不推倒重来。
3. **禁止假实现**：每条改进都必须可运行、可复现验证；UI 改动必须真实跑一遍（环境支持时），否则标注「待验证」。
4. **禁止私自扩大范围**：一次只做一条改进项，做完验收再动下一条，防止互相干扰。
5. **保留证据**：每次改动运行 `python -m unittest discover -s tests -v` 并保留输出；Release/打包类改动必须重打 exe 并离屏冒烟。
6. **数据安全**：SQLite 结构变更必须带迁移（`ALTER TABLE ... ADD COLUMN` 判断式迁移），禁止直接删表。
7. **保持依赖最小**：新增第三方库必须论证必要（如 PyGithub 已因 multipart 坑而必要），并在 requirements 中显式声明。
8. **版本管理**：完成 M1 后 `bump gcm/__init__.py __version__ → 2.0.0`，打 tag `v2.0.0`，更新 README「功能」表与截图。

## 六、验收总则（文档如何算闭环）

最终交付判定：**每条改进项都有「验收」栏的真实运行输出或离屏证据**；所有测试绿、无 P0 残留；`README.md`、`workflow_status.md` 与代码现状一致；exe 重新打包且通过离屏冒烟；Release 为最新版。

> 如果你（实施 AI）对某一条的实现细节有更好的方案，允许偏离本文档，但**必须**：在改动前记录替代方案与理由（写入 `workflow_status.md`），并保证验收标准等价或更高。

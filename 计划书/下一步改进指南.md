# Git-clone-Max 下一步改进指南（v2.0.2 → v3.0 迭代路线图）

> 文档定位：本项目**唯一权威**的迭代升级计划书，供任意 AI 开发者按此实施（本仓库 `计划书/` 文件夹统一存放路线图、PRD、技术方案等规划文档）。
> 当前基线版本：**v2.0.2**（已发布 Release，exe 已上传 GitHub，含本地仓库导入 + 增量更新 + 管理页虚拟模型提速）。
> 本文档基于对 **v2.0.2 全量源码的二次审查**（`gcm/` 全部模块 + `tests/` + 构建/发布脚本），逐条附 **文件:行 证据** 与 **可复现验收**，杜绝"假实现"。
> 分级编排：**P0 必修（正确性）→ P1 重要（性能/体验）→ P2 增强（功能扩展）→ P3 远期（生态/突破）**。版本不受上限约束：本路线图全部落地后即 v3.0，此后按同一框架持续迭代（v3→v4→…）。

## 二、v3.0 改进路线图（按优先级）

> 实施顺序建议：**P0 全做 → P1 按依赖 → P2 按价值 → P3 按规划**。每条含：问题与证据 / 根因 / 方案（函数级）/ 改动文件 / 验收（可复现）/ TDD 用例。允许对方案细节做更优替代，但必须先在 `workflow_status.md` 记录理由，且验收标准等价或更高。

### P0 — 必修：正确性与可靠性（第一优先级）

#### V3-P0-1 一键更新携带真实 local_path（修 B1）

- **问题与证据**：`update_all`（`main_window.py:524-526`）与 `_update_next_root`（`:539-541`）构造 `RepoSpec` 时只有 `owner/repo/url_https/folder_name`，未带 `local_path`。导入仓库的真实目录若与 `root/folder_name` 推导不一致（非规范命名、深路径、改名过）→ `GitService._repo_dir`（`service.py:293-297`）找不到 → 误克隆或更新错目录。
- **根因**：v2 导入功能只修了"导入后立即同步"路径，`update_all` 这条入口漏改，属于**半闭环**。
- **方案**：
  1. 抽一个函数 `_rows_to_specs(rows) -> List[RepoSpec]`，统一从 DB 行构造：`RepoSpec(owner=r["owner"], repo=r["repo"], url_https=r["url"], folder_name=r["folder_name"], local_path=r.get("local_path") or "", is_local=not bool(r.get("url")))`。
  2. `update_all` 与 `_update_next_root` 全部改用它（消除两处手写构造的重复）。
  3. `_update` 对 `is_local` 已跳过 fetch，行为不变；对 `local_path` 非空仓库 `_repo_dir` 直接命中真实目录。
- **改动文件**：`gcm/ui/main_window.py`、`gcm/models.py`（无需改，字段已在）。
- **验收**：① 建一个非规范命名（如 `my-proj`）的本地仓库目录，导入 → 管理页点「一键更新全部」→ 日志显示走**增量 fetch** 而非"开始克隆"；② 远端推新提交 → 一键更新 → `+N 提交`；③ 该目录下不产生重复克隆目录。
- **TDD 用例**（`tests/test_main_window_update.py`）：
  - `test_update_all_specs_carry_local_path`：DB 写入 `local_path=/x/my-proj`、`url=""` 的记录 → 调 `_rows_to_specs` → 断言 `spec.local_path == "/x/my-proj"`、`spec.is_local is True`。
  - `test_update_all_specs_carry_url_for_remote`：有 `url` 的记录 → `is_local is False` 且 `url_https` 保留。
  - `test_empty_local_path_fallback`（修 B10）：`local_path=""` 时 `is_local = not url` 不崩、`folder_name` 兜底（P0-1 一并覆盖）。

#### V3-P0-2 worker 落库保留原始 host（修 B2）

- **问题与证据**：`worker.py:63` `upsert_repo(spec, res.path, host="github.com")` 硬编码；导入仓库 host 为 `local`/`gitlab.com` 等（`local_repos_dialog.py:225`），一旦跑同步即被改写，与既有记录产生 `UNIQUE(owner,repo,host)` 重复（`repo_db.py:31`）。
- **根因**：`CloneWorker` 不知道来源 host，同步完成落库时用默认值覆盖。
- **方案**：
  1. `TaskPayload` 增加 `host: str = "github.com"` 字段（`worker.py:27-30`）。
  2. `_launch`（`main_window.py:577-591`）构造 payload 时，从 DB 查该仓库原 host（`self.db.get_repo(...)` 或构造 specs 时带出），查不到才用 `"github.com"`。
  3. `CloneWorker.run` 的 `upsert_repo` 改传 `self.payload.host`。
- **改动文件**：`gcm/app/worker.py`、`gcm/ui/main_window.py`。
- **验收**：导入 1 个 local 仓库 → 一键更新 → 管理页仍只有 **1 条** 记录且 host 为 `local`；DB 中 `SELECT COUNT(*) FROM repos WHERE owner=? AND repo=?` 为 1。
- **TDD 用例**（`tests/test_worker.py` 追加）：
  - `test_worker_upserts_with_payload_host`：构造 `TaskPayload(host="local")` 的 worker → run → 断言 DB 记录 host == "local"。
  - `test_imported_repo_no_duplicate_after_update`：导入 local 仓库 → 跑 sync → `count` 仍 1。

#### V3-P0-3 浅克隆仓库增量更新修复（修 B3）

- **问题与证据**：`main_window.py:194-199` 提供浅克隆选项，但 `_clone`（`service.py:357`）与 `_update`（`:401-404`）均未携带 `--depth`/`--unshallow`。shallow 仓库 fetch 后 merge 报 "shallow update not allowed"。
- **根因**：git 对 shallow 仓库的增量更新需要显式 depth 语义，当前 `git fetch --prune origin` 对 shallow 仓库不成立。
- **方案**：
  1. `Settings` 增加 `shallow_fetch: bool = True`（浅克隆仓库增量 fetch 时保持浅层）与 `fetch_unshallow: bool = False`（可选：一键拉全历史）。
  2. `GitService._update` 先检测浅层标记：`repo_dir/.git/shallow` 存在（或 `git rev-parse --is-shallow-repository` 输出 true）。
  3. 浅层时 fetch 命令改为 `git fetch --prune --depth=<已配置深度> origin`（深度取 `Settings.depth`，未配置则保持现有浅度 `--depth=1`）；若用户开启"拉全历史"则 `git fetch --prune --unshallow origin`。
  4. `_clone` 支持 `depth` 参数（`git clone --depth=N`），并把 `depth` 从 `_launch` 透传进 `GitService`。
- **改动文件**：`gcm/db/settings.py`、`gcm/git/service.py`、`gcm/ui/main_window.py`。
- **验收**：① 用 `--depth=1` 浅克隆一个真实仓库 → 一键更新（远端新增 1 提交）→ 成功 `+1 提交`，无 "shallow update not allowed"；② 开启"拉全历史"后再次更新 → 变全量，`git rev-list --count HEAD` 与远端一致。
- **TDD 用例**（`tests/test_core.py` 追加，真实裸仓库）：
  - `test_shallow_clone_then_incremental_update`：`git clone --depth=1 file://...` 造浅层 → 远端加提交 → `sync` → SUCCESS 且 commits==1。
  - `test_unshallow_option_pulls_full_history`：开启 unshallow → `rev-list --count` 增长到全量。
  - `test_shallow_detection`：造 `.git/shallow` → `_is_shallow_repo` 返回 True。

#### V3-P0-4 本地路径远端增量更新（修 B4）

- **问题与证据**：`scanner.to_spec`（`scanner.py:186-194`）`is_local = not url`，`file://`/`C:/x` 远端 → `url_https=""` → 判纯本地 → `service.sync`（`service.py:324-333`）跳过 fetch。此类远端实际可 fetch 增量。
- **根因**：`is_local` 语义被混用：既指"无任何远端"，又间接吞掉了"本地路径远端"。
- **方案**：
  1. `scanner.to_spec`：`is_local = not (info.remote_url or info.url_https)`；`url_https` 兜底改为 `info.remote_url or info.url_https or info.path`。
  2. `service.sync`：`spec.is_local` 分支保持；`_update` 对本地路径远端直接 `git fetch --prune origin`（git 原生支持）即可完成增量，无需改动合并逻辑。
  3. `RepoSpec` 增加注释明确 `is_local` 定义："无任何远端 URL（纯本地）"。
- **改动文件**：`gcm/app/scanner.py`、`gcm/git/service.py`（仅注释/兜底）、`gcm/models.py`。
- **验收**：建裸仓库 `D:/remote.git`，克隆为工作仓库 → 从工作仓库扫描导入 → 裸仓库推新提交 → 一键更新 → `+1 提交` 且 HEAD 一致（不再显示"本地仓库（无远端）"）。
- **TDD 用例**（`tests/test_scanner.py` 追加）：
  - `test_to_spec_file_url_not_local`：`RepoInfo(remote_url="file:///d:/remote.git")` → `is_local is False` 且 `url_https` 非空。
  - `test_to_spec_local_path_remote_keeps_fetchable`：`remote_url=r"C:\remote.git"` → 同上。
  - `test_to_spec_truly_local`：`remote_url=""` → `is_local is True`。

### P1 — 重要：性能与体验（第二优先级）

#### V3-P1-1 日志洪峰节流（修 B5）

- **问题与证据**：`LogModel.append` 每行 emit（`theme.py:124-130`），主窗口每行 `appendPlainText` + 滚动跟随（`main_window.py:379-393`）。高频 git 输出时主线程刷屏卡顿。
- **方案**：
  1. `LogModel` 增加批量接口 `append_many(entries)`；`append` 内部仍兼容单条（保留信号语义，避免破坏现有测试）。
  2. `MainWindow` 增加节流：`_log_pending: list` + `QTimer(100ms)` 单次触发 `_flush_log`（合并追加 + 一次滚动跟随）。任何 `log.append` 只入 pending，由定时器 flush。
  3. 日志条目级别过滤（补上轮 P2-2 缺口）：日志区加「级别」下拉（全部/INFO/WARN/ERROR/SYSTEM），`_flush_log` 按当前过滤渲染。
- **改动文件**：`gcm/ui/theme.py`、`gcm/ui/main_window.py`。
- **验收**：注入 5000 条日志 → UI 不卡（离屏冒烟：`QTest.qWait` 下主线程响应 < 100ms 级）；过滤"仅 ERROR"后仅错误行显示；`log_count` 数字正确。

## 三、实施顺序与里程碑（依赖关系）

```
里程碑 M1（正确性，本轮必做）＝ V3-P0-1 + V3-P0-2 + V3-P0-3 + V3-P0-4
里程碑 M2（性能/体验）＝ V3-P1-1 → V3-P1-2（依赖 P1-1 节流底座）→ V3-P1-3 → V3-P1-4 → V3-P1-5 → V3-P1-6
里程碑 M3（功能扩展）＝ V3-P2-1（依赖 P0-2 的 host 链路）→ V3-P2-2 → V3-P2-3 → V3-P2-4 → V3-P2-5 → V3-P2-6 → V3-P2-7 → V3-P2-8 → V3-P2-9 → V3-P2-10
里程碑 M4（生态）＝ V3-P3-1 → V3-P3-2 → V3-P3-3 → V3-P3-4 → V3-P3-5 → V3-P3-6
```

依赖关系：
- `V3-P0-2（host 传递）`是 `V3-P2-1（多平台）` 的前置——多平台解析出的 host 必须能完整落库与回传。
- `V3-P1-2（任务表虚拟化）`依赖 `V3-P1-1` 先解决日志洪峰（否则模型化后仍被日志拖慢，无法证明收益）。
- `V3-P1-6（详情页）`直接复用管理页 `ManageRow` 数据与 `db.history`，无新依赖。
- `V3-P3-1（CI）`应在 P0/P1 稳定后配置，避免每个 PR 触发昂贵打包。

**每完成一个里程碑都必须：** 全量跑测试套件（`python -m unittest discover -s tests -v`）+ 离屏冒烟（`QT_QPA_PLATFORM=offscreen` 起窗口）+ 若改发布/打包相关再重打 exe 并离屏验证 + 更新 `workflow_status.md` 与 README「功能」表。

5. **保留证据**：每次改动运行全量测试并保留输出；性能类改动记录**改动前/后基线**；打包类改动必须重打 exe 并离屏冒烟。

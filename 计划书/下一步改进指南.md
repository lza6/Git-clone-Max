> 版本日期：2026-09-09
> 范围：并发架构 / 闪退根因 / 一致性 / 平台兼容 / 发布 / 长期迭代
> 原则：**只改必须改的，不重写已有轮子**。在现有 `gcm/` 多模块结构上**收敛、加锁、加边界**，不做大规模重构。

## 一、任务背景与目标

**核心目标（用户原话归纳）**
1. 并发一高软件会闪退 —— 必须解决并发竞态导致的锁死/崩溃。
2. 拉满最大速度 —— 并发能力要真正可控可拉满（当前默认 8、上限 16 且与设置逻辑脱节）。
3. 一键更新与主界面「开始克隆」并发行为不一致 —— 统一调度。
4. 弄清 layerfs 克隆失败根因 —— 平台限制识别 + 友好降级，不重试无效操作。
5. 真实 E2E 测验、验收、审计 —— 全链路跑通、覆盖率达标、可复现证据。
6. 提交推送仓库、创建发行版 —— 版本 bump + tag + Release 发布。

**成功标准**
- 高并发（32 线程）批量克隆不再闪退 / 不再永久卡死（busy 锁死）。
- 同一仓库重复提交自动去重，不再出现两个 worker 抢同一目录。
- `progress.json` 多 worker 并发写安全，finished 信号永不丢失。
- SQLite 高并发写不再 `database is locked`。
- 主界面「开始克隆」与「一键更新全部」走同一调度引擎，并发设置实时生效。
- 含 Windows 非法路径的仓库（如 `layerfs:ai-native-file-system.html`）失败原因清晰可读。
- 全量测试通过、覆盖率 ≥ 80%，新增并发 E2E 用例。
- 版本 bump 到 4.0.0，tag `v4.0.0` 并发布 Release（exe 附件 + 校验）。

## 三、根因分析（闪退 / 不一致 / layerfs）

### 3.1 并发闪退根因（按置信度排序）

**根因 1（最高置信）：`progress.json` 共用临时文件 → finished 信号丢失 → UI 永久 busy**
- `save_progress`（`repo_db.py:189-193`）：`tmp = path.with_suffix(".json.tmp")` 是**全局唯一路径**。
- `CloneWorker.run.finally`（`worker.py:89-100`）：每个 worker 都 `load_progress → 删除旧 key → append → save_progress`，最后 `self.signals.finished.emit()`。
- N 个 worker 并发完成时**同时**对同一 `progress.json.tmp` 执行 `open("w")` → Windows 下 `PermissionError`/`OSError` → **`finished.emit()` 未执行** → `_on_worker_finished` 的 `_pending_count` 永不归零 → 按钮全灰、界面「卡死」。用户感知为「闪退」。

**根因 2：SQLite 无 busy_timeout**
- `repo_db.py` 只设 `WAL` 与 `foreign_keys`，未设 `busy_timeout`（默认 0）。高并发 upsert/history 写时，WAL 锁竞争直接抛 `database is locked` → worker 异常 → 记入 failed，但 UI 侧无兜底重试。

**根因 3：同一 `folder_name` 无去重**
- `MainWindow._launch` 对输入行逐一建 worker，不检查目标目录冲突。
- 日志实证：`Ephemeral-AI-Lab/layerfs` 出现**两次**克隆指令 → 第二个 worker 报 `fatal: cannot copy … commit-msg.sample … File exists` 并**清理了第一个 worker 正在写的目录** → 双双失败。这是并发竞态的实锤。

**根因 4（次因）：`_any_cancel()` 高频调用**
- `main_window.py:794-795`：每个 git 输出行都遍历 `self.flags.values()`。32 线程 × 高频输出 → CPU 热点，加剧 UI 卡顿。

**根因 5（次因）：并发上限与设置脱节**
- `main_window.py:77` `min(16, …)` 硬编码 + SpinBox 上限 16 + 默认 8 → 「拉满速度」做不到（想设更高都被框死）。

### 3.2 一键更新 vs 开始克隆「并发不一致」的真相

**代码事实**：两条路径最终都走 `MainWindow._launch`，共用**同一个** `self.pool`（`main_window.py:76`），并发机制**同源**。感知差异来自：
1. **值域被锁死**：上限 16、默认 8，任何路径都拉不满；
2. **输入规模**：一键更新一次性拉起 DB 全量（如 7 个仓库）线程全开；开始克隆用户通常只输入几个 → 感觉「没并行」；
3. **一键更新仓库多 → 并发完成集中 → 更易触发根因 1 的锁死**，进一步放大「不一致」观感。

**结论**：不是两套并发机制，而是**缺一个统一调度器 + 值域放开**。这决定了方案 B 的方向：新建 `SyncEngine` 统一入口。

### 3.3 layerfs 克隆失败根因（两条独立原因，日志实证）

1. **重复提交（并发竞态）**：输入框含重复行 → 两个 worker 抢同一目录 → 第二个 `File exists` → 各自清理 → 都失败。修复：**去重**。
2. **Windows 非法文件名**：仓库含 `docs/research/vision/layerfs:ai-native-file-system.html`，Windows 禁止冒号文件名 → `fatal: invalid path … unable to checkout working tree`。这是 **Windows 平台限制**，任何 git 配置都还原不了（`core.protectNTFS` 只防安全校验，不解决合法字符限制）。浅克隆（`--depth 1`）同样在 checkout 阶段失败。

**处理策略（不做无效重试，友好降级）**：
- 失败原因识别：`invalid path` / `File exists` 单独解析，输出人类可读提示；
- `File exists` → 提示「目录被占用：可能重复提交或残留，已自动去重/清理」；
- `invalid path` → 提示「该仓库含 Windows 不允许的文件名，无法在 Windows 检出；可换 WSL/Linux/Codespaces」；
- 不重试平台限制类错误（`_is_networkish_error` 已排除，`invalid path` 应同样加入「不重试」清单）。

## 四、设计方案（方案 B：统一调度器 + 共享资源锁 + 失败恢复）

> 在不重写现有轮子的前提下，新增一个薄调度层，把已有能力（GitService / Database / progress / worker）**串起来并加锁**。

### 4.1 新增模块 `gcm/app/engine.py`：SyncEngine

**职责**：统一「开始克隆 / 一键更新 / 并发调整 / 取消 / 断点续传」调度。UI 只依赖它，不再各自拼装。

```
class SyncEngine(QObject):
    progress = pyqtSignal(int, str)        # index, percent
    line     = pyqtSignal(int, str, str)   # index, text, level
    result   = pyqtSignal(int, SyncResult)
    finished = pyqtSignal()

    def __init__(self, root: Path, db: Database, progress_path: Path, settings: Settings): ...
    def set_concurrency(self, n: int): ...
    def launch(self, specs: list[RepoSpec], host_by_key: dict[str,str],
               fetch_depth: int, unshallow: bool, clear_input: bool=False,
               multi_root_relay: bool=False) -> None: ...
    def cancel_all(self) -> None: ...
```

**要点**：
1. **去重**：`launch` 内按 `(folder_name 或 local_path)` 去重，重复地址只同步一次，其余标 `SKIPPED` 并记录原因；避免根因 3。
2. **统一并发**：`set_concurrency` 直接 `pool.setMaxThreadCount`，值域 1–32（来自设置，不再硬编码）。
3. **持锁写进度**：progress 写入集中到 engine 的**周期 flush**（每 2s），worker 只把结果回传 engine；engine 单线程写文件 → 消除并发写同一 tmp 的竞态。
4. **取消收敛**：`cancel_all` 只标记 flags；engine 提供 `is_cancelled(key)` 缓存，替代 `_any_cancel` 每行遍历。
5. **finished 统计**：engine 内部计数 worker 完成数，全部完成才 emit `finished` → 不再依赖「finished 信号逐个递减」（根因 1 的二次防线）。

### 4.2 progress.json 并发安全（`repo_db.py` 增强）

- **内存聚合 + 周期落盘**：engine 持有一份 `_progress` 内存态；worker 完成即回传，engine 每 2s 或全部完成时 `save_progress` 一次。
- **进程级文件锁（Windows 用 msvcrt / 跨平台 fallback）**：`save_progress`/`load_progress` 外层加互斥，保证即使多实例也安全。新增 `_file_lock(path)` 上下文管理器（`msvcrt.locking` on nt，`fcntl.flock` on posix，失败降级为线程锁）。
- **保留 `mark_finished`/`load_progress` 现有接口**（测试/外部依赖），内部实现加锁。

### 4.3 SQLite 并发（`repo_db.py`）

- `connect` 后执行 `PRAGMA busy_timeout=30000`（低风险、一行）。
- 写事务合并：worker 不再逐行 commit；engine 在 worker 完成回调里一次性 `upsert_repo + add_sync_history`（现状 worker 内已是两次写，可保留，靠 busy_timeout 兜底；优化为批量亦可）。

### 4.4 UI 接入（`main_window.py`）

- 用 `SyncEngine` 替换 `_launch`/`update_all` 内部拼装逻辑；`self.pool` 收敛进 engine。
- `_on_worker_result` / `_on_worker_finished` 改为监听 engine 信号（保持现有表格/日志渲染不变）。
- `_any_cancel` 删除，改走 `engine.is_cancelled`。
- SpinBox 并发上限从 16 → **32**；`_save_concurrency` 调用 `engine.set_concurrency`。
- 主界面 `mode_combo`（满量/浅克隆）+ `depth_spin` 的状态在 `launch` 时传入 engine（修复「开始克隆不传浅克隆语义」的隐患）。

### 4.5 失败原因识别（`gcm/git/service.py`）

- 在 `_clone`/`_update` 的失败路径，用 `_classify_failure(tail)` 解析：
  - `invalid path` → 平台限制提示（Windows 非法文件名），`message="仓库含 Windows 不允许的文件名，无法检出"`，detail 带文件路径；
  - `File exists`（且目标目录存在）→ `message="目录已存在（重复提交或残留），已自动去重"`；
  - 其余走原有网络/仓库分类。
- `_is_networkish_error` 之外的平台限制类错误**不重试**（加入不重试清单）。

### 4.6 断点续传语义保持

- 现有 `progress.json` 的 `finished` 项在 `launch` 时预检：已完成且目录存在 → 直接标 SKIPPED/SUCCESS 不再 clone（保留现有行为，由 engine 收敛实现）。

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 加锁引入死锁/性能回退 | 高并发场景变慢 | 锁粒度尽量小；周期落盘而非逐 worker 锁；覆盖并发 32 测试 |
| `msvcrt` 在非 Windows 不可用 | 跨平台测试 | 封装 try/except 降级为线程锁 + 平台分支 |
| engine 改动破坏现有 UI 测试 | 回归 | 保留 `MainWindow` 对外接口签名（`_launch` 语义不变），内部换实现；跑全量 `test_ui.py` |
| layerfs 类平台限制再次出现 | 用户困惑 | 失败原因识别 + 明确提示，不重试 |
| 发布 token 不可用 | 无法上传 Release | 走 `git credential manager`（已配置 `credential.helper=manager`）；dry-run 先行校验 |

## G68 轮发现与修复（均有一手证据，非静态推断）

### G68-2 `cross_process_lock` 重入判断错误 → **不同路径嵌套时内层文件锁被完全跳过**（P1）

原实现用「本线程重入深度」判断是否跳过文件锁。但重入语义应当**按路径**：
`RLock` 可重入、文件锁不可重入 —— 同一路径重入必须跳过（否则 msvcrt 自锁死等），
而**不同路径**嵌套时若也跳过，那条路径就毫无跨进程保护。

**实测（两进程 + 区间重叠判定）**：P1 持锁 A 后进入锁 B（不同路径），P2 独立抢占 B ——
修复前 `P1[0, 2.51s]` 与 `P2[1.43, 3.94s]` **重叠 1.08 秒**，两个进程同时在 B 上读-改-写；
修复后 P2 在 P1 结束后 0.74s 才进入（不重叠）。

> 判定方式刻意用**区间重叠**而不是「最终计数」：计数依赖两次操作恰好交错，
> 进程启动耗时会让它**假 PASS**（本探针第一版就是这么假通过了一次）。

### G68-3 `sanitize_name` 不处理 Windows 保留设备名 → 归档必失败且报错误导（P1）

`_INVALID_DIR_CHARS` 只过滤 `\ / : * ? " < > |` 与控制字符，**没管 CON/PRN/AUX/NUL/COM1-9/LPT1-9**。
这些名字不能作文件/目录名，而归档路径用的是 **URL 末段**（`archives/<末段>.zip`）：

```
git archive --format=zip --output archives/CON.zip HEAD
→ rc=128  fatal: could not open '.../CON.zip' for writing: No such file or directory
```
用户粘贴 `https://github.com/foo/CON` → 点「归档」→ 必然失败，而错误信息会让人以为是网络/权限问题。
**克隆不受影响**（目录名是 `owner__repo`，永不等于设备名），所以只在归档时暴露。

**第一版修复是错的**（已用真实命令证伪并纠正）：把 `_` 追加到**末尾** →
`CON.txt` → `CON.txt_`，点前段仍是 `CON`。实测：

| 目标文件名 | 真实 `git archive` 结果 |
|-----------|------------------------|
| `CON.txt.zip` | rc=128 失败 |
| `CON.txt_.zip` | rc=128 **仍失败** |
| `CON_.txt.zip` | rc=0 成功 |

修复改为改写**第一个点之前的那一段**。另注意：**Python `open()` 在本机对保留名不报错**
（3.14 用 `\\?\` 前缀绕过 DOS 设备名解析），所以只有用真实工具（`git archive` / `mkdir`）
才测得出来 —— 「用 Python 打开成功」不能作为该问题的判据。

### G68-4 窗口不可见时仍弹模态 → **headless 下永久阻塞进程**（P1，实测挂死 7 分钟+）

`update_checked` 是**跨线程异步**信号（G67-9 从同步改为异步桥）。某个测试发起检查后没等槽执行就结束，

## 压测（G69 高并发轮）抓出的 3 处并发缺陷

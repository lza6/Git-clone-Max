## 1. C3-4 分阶段耗时（补完 C3）

| 项 | 内容 |
|---|---|
| 问题 | `sync_history` 只有整仓总时长。用户报「今天全都慢」时只能翻 git 原始日志猜是 DNS/TLS、探测、传输还是检出 |
| 修法 | `SyncResult.stages` 记 `precheck` / `transfer`（**含全部重试与降级链**）/ `checkout` / `hook`；落 `sync_history.stage_json`（**schema v7**）；`db/stage_stats.py` 提供 `slow_stages()`（最慢仓库）与 `stage_totals()`（各段累计，已接进诊断报告） |
| 埋点方式 | 一个 `_timed(res, name, fn)` 包住「传输/更新」与「检出」两个调用点 —— **不在 `run_git_ui` 的 5 处调用里逐处插桩**（漏一处就失真） |
| 守卫 | `test_c3_data.TestStageTiming`（5 例，含**真实本地克隆**断言 `transfer`/`checkout` 两段都有值） |

## 2. C4 双路检索（4 项全做）

| 项 | 内容 |
|---|---|
| C4-1 双路 | `db.search_repos` 收口：**≥3 字符走 FTS5**（bm25 排序），**<3 字符走 LIKE 下推**（3000 行实测 3.9ms）。两条路返回同形状的行 |
| C4-2 派生索引 | `repo_fts` = `content='repos'` 的 FTS5 **外部内容表**（trigram）；**无触发器**，由 `ensure_fts()` 在启动与每批结束各对齐一次；索引缺失/查询异常/无 FTS5 环境 → **自动降级 LIKE**，应用照常可用 |
| C4-3 查询语法 | 纯函数 `parse_query`：`tag:` / `host:` / `favorite:` / `updated:<30d` / `-` 负向；tag 按**逗号边界**匹配（`tag:py` 不命中 `python`）；`lang:`/`size:`/`archived:` **明确报「不支持」** |
| C4-4 三出口共用 | 管理页过滤 / `GET /api/repos/search` / MCP `search_repos` 都走同一个 `search_repos`（后两者无需改动） |

**为什么必须双路（Rev7 §2.1 的实测修正）**：FTS5 的 `trigram` 要求查询 **≥3 个 unicode 字符**，
实测 `'克隆'`/`'机器'`/`'学习'` 全部**零命中**，只有 `'机器学'` 命中 —— 照抄"纯 trigram"方案
会在上线当天被报「搜索坏了」。中文最常搜的恰恰是两个字。

## 4. 兼容与迁移

| 面 | 结论 |
|---|---|
| v6 → v8 | v7 只给 `sync_history` 加一列；v8 只新建 `repo_fts` 虚表。**都是加性**，旧库自动迁移，幂等 |

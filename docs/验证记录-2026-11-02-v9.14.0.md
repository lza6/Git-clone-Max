## 2. 规模与泄漏实测（脚本真跑）

### 2.1 `scripts/bench_scale.py`

| 指标 | 1000 仓 | 3000 仓 |
|---|---|---|
| `db.list_repos()` 全量 | 3.91 ms | **14.18 ms** |
| `db.list_repos_page(50)` | 0.38 ms | 0.71 ms |
| `db.search_repos()`（LIKE 下推） | 1.01 ms | 3.90 ms |
| `ManageModel.set_rows()` | 1.21 ms | **4.09 ms** |
| 表格首帧（3×processEvents） | 0.05 ms | 0.14 ms |
| `dir_stats` 命中（批量） | 1.14 ms | **3.92 ms** |

`prune_history` @ **10 万行** = **238 ms**（这也是 C3-2 要把它挪出热路径的理由）。

> **顺手否决一个旧假设**：3000 仓库下「取全量 + 建模 + 首帧」合计约 **18ms**，
> 远低于可感知阈值 —— **分页不是当前瓶颈**，真正的瓶颈是 `dir_size` 的递归 stat。

### 2.2 `scripts/mem_soak.py`

| 轮数 | tracemalloc 当前 | 峰值 | 事件缓冲 |
|---|---|---|---|
| 500 | **276.4 KiB** | 294.4 KiB | 700（events 500 + progress 200） |
| 2000 | **279.7 KiB** | 297.7 KiB | 700（同上） |

**轮数 ×4 而内存几乎不变** → 事件环形缓冲有界，该链路无随轮数增长的累积。
（`psutil` 未安装时脚本只报 tracemalloc，RSS 列显示 0 —— 属预期降级。）

## 4 缺陷详单（含证据与建议修法）

### F1 [P1] 小屏下「下载位置 / 克隆模式 / 层数」被裁到只剩 6–23px

**证据**（几何断言，不是目测）：
```
1024×768 : target_edit 352x6/352x34   mode_combo 335x6/335x34   depth_spin 146x8/146x37
1280×800 : target_edit 608x23/608x34  mode_combo 335x23/335x34  depth_spin 146x25/146x37
1366×768 : target_edit 694x6/694x34   mode_combo 335x6/335x34   depth_spin 146x8/146x37
1440×900 : 无裁切
```
**影响**：1366×768 是最常见的笔记本档。用户打开就看到一个「只有一条边」的输入框，点不准、看不出是输入框。虽然顶部区**可滚动**（滚一下就能看全），但第一眼像渲染坏了；而且目标用户是「小白用户」（README 定位）。
**根因**：`_apply_layout_mode` 在 S 档把 `download_top_scroll` 最小高压到 120（矮窗 64/40），而滚动内容第一屏需要「仓库地址」+「下载位置/克隆模式」两行，装不下 → 第二行被切在控件中间。
**为什么守卫没抓到**：`test_ui_compact_visibility` 的契约清单只覆盖主操作区与工具行（16 个控件），**不含这三个**。
**建议修法**（按风险从低到高）：
1. 最小改动：把 `target_edit`/`mode_combo`/`depth_spin` 加进 `test_ui_compact_visibility` 的契约清单 → 先让它红，再决定改法（D27 顺序：先红再绿）。
2. 布局改法：把「下载位置 / 克隆模式」**移出滚动区**，与主操作区同级（照抄 X-4 对「清单行」的处理：常用控件不放进可滚动区）。
3. 保守改法：S 档把顶部滚动区最小高从 120 提到约 210（两行完整高度），代价是进度表少约 90px。

### F2 [P1] 断点续传跳过的仓库不产生终态 → 行永远「等待中」，上一次结果被清空

**复现**（真实 GUI，两次点击同一个已克隆仓库）：
```
第1轮结束 : 状态='成功' 本次='新建克隆' 详情='克隆完成' 耗时='2.6s'
[通知] 全部任务完成: 成功 0 · 冲突 0 · 失败 0
第2轮开始后: 状态='等待中' 本次='—' 详情='—' 耗时='—'
第2轮结束  : 状态='等待中' 本次='—' 详情='—' 耗时='—'
状态栏消息: 并行同步中：1 个仓库…      ← 批次已结束，消息还停在"同步中"
```
**根因**（`gcm/app/engine.py:~1036-1057`）：
```python
if not first.is_local:
    pre = self._precheck_skip(first)
    if pre is not None:
        self._emit_line(len(unique_specs), f"{first.display}：{pre[1]}", "info")   # 只写日志
        self._mark_done(key, pre[0], pre[1])                                      # 只记进度
        continue                                                                   # 不 emit result
if not unique_specs:
    self.flush_all_buffers(); self.busy = False; self.finished.emit(); return 0    # 0 结果的"完成"
```
UI 侧已经预填了行（「等待中」占位），引擎跳过时不发 result → 该行永远停在占位态。
**影响**：用户贴一批「已经下过」的仓库点「开始」，界面表现是：结果被抹成「—」、状态永远「等待中」、通知说「成功 0」、状态栏一直说「并行同步中」。既看不到「已跳过」的原因，也丢了上次的耗时。对一个「挂着刷几百个仓库」的工具，重复贴同一份清单是很常见的操作。
**建议修法**（保持「跳过判据只有一处」）：
- 引擎侧：`_precheck_skip` 命中时**照发一条 result**（`status=SKIPPED`，`message="已完成，跳过（…）"`，`duration_ms` 从 DB 取上次值），但用一个 `report_skipped: bool = False` 参数控制，GUI 传 True、CLI 保持 False（CLI 的 `results[]` 契约不变）。
- UI 侧配套：`_on_engine_finished` 无论结果数是否为 0 都要刷新状态栏（清掉「并行同步中」）。
- 守卫：一条「连续两次点开始，第二次行状态必须是 已跳过 且 耗时不丢」的 E2E。

### F3 [P2] 状态栏被「并行同步中」覆盖掉批次小结（重入顺序问题）

**现象**：0 结果批次结束后状态栏停在「并行同步中：1 个仓库…」，而正常批次显示「完成：成功 1 · 冲突 0 · 失败 0」。

**根因（读码确认，非猜测）**：`progress_table.py:683` 在 `_on_engine_finished` 里**无条件**写批次小结；
但 `engine.launch()` 在全被跳过时会**同步** `finished.emit()`（`engine.py:~1057`）——
槽先跑、写下「完成：成功 0…」，随后 `_launch` 继续往下执行到 `main_window.py:2523-2525`
又写了一次「并行同步中：N 个仓库…」，把小结**覆盖**掉。
**建议**：`_launch` 里把「并行同步中」写在 `engine.start()` **之前**，或只在 `launched > 0` 时写；
并加一条断言「0 结果批次结束后状态栏必须是批次小结」。

### F7 [P2] 顶部「输入区 + 下载位置 + 克隆模式」在任何分辨率下都需要滚动

**实测**（`download_top_scroll` 视口 vs 内容需求）：
```
1920×1080 : 视口 226 / 内容需要 298  → 需要滚动
1440×900  : 视口 222 / 内容需要 298  → 需要滚动
1366×768  : 视口 170 / 内容需要 296  → 需要滚动
1024×768  : 视口 170 / 内容需要 296  → 需要滚动（且切在控件中间，见 F1）
```
**影响**：即使是 1080p 大屏，用户也**永远看不到完整的输入区+选项区**，`克隆模式`下拉长期藏在折叠线以下。
对一个"每天都要粘地址、选模式、点开始"的工具，最高频的三件事被塞进一个永远滚动的容器里。
**根因**：`_apply_layout_mode` 用 `_top = max(240, min(420, h*0.55))` 给顶部区分配高度，
而顶部区**自身的 `minimumSizeHint` 已经 298**（三行表单 + 组框内边距）—— 分配值总是小于需求。
**建议**：顶部区的高度下限应取 `min(内容需求, 视口可用 - 进度表最小需求)`，而不是固定 55%；
或按 F1 方案把「下载位置/克隆模式」移出滚动区（移出后内容需求降到 ~200，各档都不再需要滚动）。

### F4 [P2] 管理页「健康 5/5」无解释（既有开放项，未闭环）

`.agent/memory/known-issues.md` #9 仍列为开放。截图里 12 行全是 `5/5`，用户无法知道这 5 分是什么、怎么算、为什么满分。
**建议**：给健康列挂 tooltip（六维来源 + 扣分原因），或双击进详情看雷达图（雷达图已有）。

### F5 [P3] 进度列百分比在极小/极大值时文字位置不一致

`progress_delegate` 把 `f"{pct}%  {detail}"` 居中画在整列 rect 上，但进度条填充宽度随 pct 变化 → 0% 时文字像贴在条外、56% 时在条内。
**建议**：文字与条分离（条在下、文字固定右侧），或给 0/100 两个端点特判。

### F6 [P3] 验收基础设施的数据洞（见 §3.B.5）

截图种子不建真实目录、不给 `head_sha`/`duration_ms` → 3 个数据列永远空 → 截图验收看不见它们坏没坏。

## 5. 方案对比与权衡

> 目标：在「功能已经极其丰富（88 模块 / 137 测试文件 / 33 条接缝）」的前提下，决定下一轮把力气花在哪。

### 方案 A｜工程治理与配置真实性收口（**Recommended**）

清掉**会让后续 AI 与人犯错**的东西，并补上**守卫的盲区**：

1. 仓库卫生：3.6 MB 截图出库 + 2 个根目录死文件 + 12 个日志残留。
2. 文档一阶事实漂移（8 处）+ `test_ledger` 回填 + `workflow_status §27` 过时结论更正。

4. **守卫盲区修补（P1-2）**：把 `TestG69_18NoZombieSettingsFields` 的口径从「任意同名 Identifier」收紧到「`.field` 属性访问 + `getattr(x,"field")`」，并做变异实验证明它能抓到 `depth`。
5. `settings_groups.py` 越线预防（距 800 红线仅 17 行）。

- **优点**：风险最低（唯一动生产代码的是删/接一个字段，可单测覆盖）；直接降低后续每一轮的认知成本；**修补的是「守卫生效性」本身** —— 这比修任何单个字段都值钱；可与任何功能开发并行。
- **缺点**：用户可见功能零增加；P1-2 收紧口径后**可能暴露更多历史僵尸字段**（需要一并处置，工作量有不可预知性）。
- **成本**：约 1.5–2 个工作日（含验证）。
- **风险**：L1–L2。`git rm --cached` 可回滚；字段删除有守卫与测试双重保护；收紧守卫口径若误伤可用白名单登记理由（守卫已有该机制）。

### 方案 B｜主窗热点拆分（可维护性）

只拆 `MainWindow.__init__`（233 行）与 `_launch`（129 行）两个热点，行为零变化，沿用 `update_flow`/`engine_factory` 的既有抽取范式（薄方法保留、测试名不变）。

- **优点**：把「改启动链路怕崩」的风险实质降低；为后续功能腾出安放位置；先例充分（G77 已成功拆过一块）。
- **缺点**：触碰启动链路 = 回归面最大的一块；收益要等下一个功能才兑现。
- **成本**：约 1–2 个工作日（含定向回归 + 截图审计）。
- **风险**：L2。必须跑 §11 的 E1/E2/E8 全链。

### 方案 C｜测试确定性根治（Qt 引用环）

给 42 个构造 `MainWindow` 的测试加确定性收尾（`close()` → `deleteLater()` → 泵空事件队列），逐步移除 `ci_run_fast.py` 的「整轮关闭自动 GC」安全网。

- **优点**：消灭随机 SIGSEGV；测试结论从「有时绿」变成「可复现」。
- **缺点**：工作量大且**收益难以量化证明**（要跑多轮全量才能证明不再崩）；中途可能引入新的时序脆弱。
- **成本**：2–4 个工作日，且需要多轮全量验证。
- **风险**：L2–L3（可能把「偶发」变成「稳定失败」，反而更红）。

### 方案 D｜产品功能扩张（数据资产化 / 技能市场 / MCP 写操作）

按 `product-brief.md` 方向 A/C 推进用户可见新能力。

- **优点**：唯一能带来用户增长与留存的方向。
- **缺点**：MCP 写操作涉 T3 高风险（公共契约 + 授权边界），必须先影响分析 + 回滚方案；数据资产化需要产品口径（索引什么、存哪、隐私边界）——**这些是该用户拍板、不该我猜的**。
- **成本**：不可估（缺产品决策）。
- **风险**：L3。

### 方案 E｜纯文档模式收尾（什么都不做，只把文档对齐）

只修文档，不动仓库索引、不动代码。

- **优点**：零风险。
- **缺点**：3.6 MB 截图和死文件继续在索引里；`settings_groups` 仍会在下一个功能开发时被迫越线拆分。**问题被推迟而不是解决。**

### 5.2 关键决策因素与推荐

**已拍板（用户 2026-10-24 决策）：选 A「工程治理与配置真实性收口」作为下一个版本主线**，B（主窗热点拆分）作为其后的紧接候选；C 与 D 不作为下一轮主线。

理由（按权重）：

1. **本轮发现了两个真实 P1，而它们恰好都在「治理」范畴内**：`Settings.depth` 是僵尸字段（P1-1），
   而**本该抓它的守卫有同名变量盲区**（P1-2）。后者比前者严重 —— 一个失效的守卫意味着
   「同类问题还会再发生，而且每次都会绿着发生」。修守卫的收益不随功能增加而折旧，修功能的收益会。
2. **本项目最大的成本不是写功能，是「搞清楚现在到底什么状态」**。8 处一阶事实漂移 + 3.6 MB 入库截图 +
   过时的阻塞登记，会让下一个 AI 在错误前提上做决策 —— 这在 `计划书/` 事件上已经真实发生过一次
   （`policy.md` §5 明文记录）。
3. **A 的每一项都可验证、可回滚**，符合 `policy.md` 的证据门禁；B 的收益确定但回归面大，适合在 A 之后
   单独一轮做，避免「治理 + 重构」混在一个提交里（`G78` 证据里就有「误用 `git add -A` 夹带并发会话改动」
   的先例，混合是事故源）。
4. **C 不应现在做**：当前已有「整轮关自动 GC」的确定性处置且实测 0 崩溃；根治它要改 42 个文件，
   而收益需要多轮全量才能证明 —— **投入产出比在最坏的时间点**。建议等某个功能 naturally 触碰
   这些测试时顺手改造。
5. **D 需要用户拍板**：数据资产化的产品口径、MCP 写操作的授权边界，都属于 `policy.md` §3.1 允许提问的
   第 2/6 条。**本轮只列清单与风险，不擅自开工。**
6. **E 被否**：它把 P2-1/P2-2/P2-4 **和两个 P1** 原样留给下一轮，而 `settings_groups` 越线是确定会发生的。

## 18. 一句话结论

## 5. 方案对比与权衡

### 方案 A｜G75 收口优先（**Recommended**）
先把**未提交的这半轮**收干净：修门禁（ruff/mypy）、拆 `progress_table`、补 `test_g75_visual_system`、
补 changelog/验证记录/行数表、跑快集与构建、出一版 9.8.x。核心原则是「**不留半成品提交**」。
优点：风险最低（改动面已被 242 条用例覆盖）、立刻让 `git status` 回到干净、避免半成品与新需求交叉污染。
缺点：**用户看不到新东西**（这一版是"把已做的做完"），且要为 3 处新模块补 ≥15 条真实断言。
约 1 个 patch 版本。

### 方案 B｜接线收口（旧指南 A）
6 个设置字段 / 扫描进度 / sha256 提示 / 数据目录入口 / 死信号，一次性「要么接线要么删」。
优点：一次性消除「文档说能做、用户做不到」（11 处），收益直接可见。
缺点：动设置页与主窗口两个高热区；与 A 有文件重叠（`main_window.py` 已被 G75 改到 2717 行），
**必须排在 A 之后**，否则两批改动混在一个 diff 里无法归因。

### 方案 C｜真机与 CI 硬化
截图审计纳入发版清单并做改前/改后对照、Windows 慢集入 CI、`e2e_smoke` 扩到失败/取消/冲突。
优点：把 B4 那种「只有人眼能发现」的问题制度化；G75 这轮**尤其需要**（渐变/高光/pill 全在离屏验的）。
缺点：CI 分钟数与人工时间上升；Windows 慢集有已知 flake 面。

### 方案 D｜agent 一等公民
本地 API 一次性 token、MCP 写工具显式授权、补 `annotations`/`outputSchema`、事件文件桥。
优点：打开生态传播面。缺点：全是公共契约变更（T3），必须影响分析 + 授权；token 一引入旧 curl 示例全废。

### 方案 E｜工程治理（去文档通胀）
行数表引用式化、文档守卫扩到 `.py` docstring、i18n 键引用守卫、`workflow_status.md` 归档。
优点：让后面每次改动更便宜，顺带消掉 B2/B3/B5 三类漂移。
缺点：纯投入，无用户可见产出。

### 5.2 关键决策因素与推荐

1. **「半成品提交」是当前最大风险**：工作区有 15 个 modified + 7 项 untracked（含 5 个新模块），
   新需求插进来就会混成不可归因的 diff。**A 必须先做**。注意门禁已在 11:00 转绿 —— 但
   **转绿 ≠ 可提交**：`progress_table` 仍 848 行、装饰器仍错位、登记面仍空。
2. **A 与 E 共享验证手段**（都要跑定向回归 + 文档守卫），可同版打包；E 的两条守卫
   （docstring 路径、i18n 引用）**顺手就能写**，建议并入 A 的收尾提交。
3. **B 的收益最大但必须串行在 A 之后**（同一批文件）。
4. **C 是 G75 的验收前提**：离屏全绿不能替代真机（B4）。
5. **D 需授权**，不由执行者决定。

**推荐顺序：A（主）+ E 轻量（同版）→ B → C → D 待授权。** 见 §6。

反向辩手：先攻击自己的上一轮工作

  1. 「功能都做了」是否等于「系统是真实的」？ —— 不等于。测试会变红、版本会漂移、编码会在别的机器上炸，这些都是「系统真实性」的一部分，却不属于任何功能。
  2. 有没有把浅实现当成完整实现？ —— 有。`--serve 0.0.0.0` 能起服务这件事，代码和文档都只写了「只绑定 127.0.0.1」，没有任何强制。这是把「默认值」当成了「安全边界」。
  3. 改了一个点，会不会破坏旧逻辑？ —— 这是本次最需要防的。所有修复都配了回归批（129 用例），并且 HTTP 回环加固特意允许端口 0（内核分配），以免打断既有测试的绑定方式。
  4. 是否默认了某些环境天然存在？ —— 有。整个 CI 只在 Linux 上跑慢集，而本机 locale.getpreferredencoding() 是 cp936。CI 永远测不出中文 Windows 的问题。

G66-4中文 Windows 下子进程解码崩溃 —— 明明克隆成功却报失败P0
现象
本机 locale.getpreferredencoding() = cp936。凡是输出中含 UTF-8 而非 GBK 可表示字符的 git 命令，读取线程直接抛异常，CompletedProcess.stdout 塌陷为 None，下游紧接着 TypeError: 'NoneType' object is not subscriptable。
复现
构造含 …(U+2026) / ®(U+00AE) / ①(U+2460) 的提交信息与文件名，跑 git log： 
Exception in thread Thread-19 (_readerthread):
  File "subprocess.py", line 1613, in _readerthread
    buffer.append(fh.read())
UnicodeDecodeError: 'gbk' codec can't decode byte 0xad in position 16
# 默认 locale：CRASH
# encoding="utf-8", errors="replace"：OK: 'dc531e9 init: 中文…®① 提交信息'
这不是假想场景：项目自己的测试套件运行时就在刷同一条 UnicodeDecodeError: 'gbk' codec can't decode byte 0xae。
影响面
全仓 26 处 subprocess.run(..., text=True) 未指定 encoding（gcm 21 / scripts 5 / tests 8），只有 3 处是对的先例（scanner.py、service.py:240）。受影响命令包括 status --porcelain / rev-parse / symbolic-ref / rev-list / ls-remote / credential fill / schtasks。只要是中文仓库（提交信息/文件名带 …、®、表情、生僻字），用户就会看到假的失败。
为什么没被发现
CI 跑在 ubuntu-latest，locale 是 UTF-8 —— 这条路径在 CI 上结构性地不可能触发。这就是「CI 全绿」在 Windows 桌面应用上的盲区。
修复
26 处全部补 encoding="utf-8", errors="replace"（沿用项目既有先例的写法，不引入新抽象，避免破坏既有 mock）。
验证
AST 静态守卫 TestSubprocessTextDecoding 覆盖 gcm/scripts/tests 三目录（返回空列表）；真实 E2E TestSubprocessDecodeE2E 用本地裸仓 + 中文提交信息跑通 _is_dirty / _divergence_info 真实产品路径。修复后快集运行日志中该 traceback 消失。

第二轮：独立审查线程追加发现的 4 个缺陷

上面 6 条是我自己审计出来的。此后按其要求启动了独立审查线程（builder ↔ critic 闭环），它们在同一份改动上又挖出 4 个真实缺陷 —— 其中 3 个是 P0，且都属于「功能写着有、实际不可用」的同一类病。以下每条都由我亲自复现确认后才修复。

G66-8文档里写的 CLI 命令 100% 崩溃；--help 静默拉起 GUI 并挂死 43 分钟P0
现象 A
python -m gcm --cli --serve 127.0.0.1:8765 —— 这正是 docs/agent-contract.md、gcm/cli.py docstring、README 三处写的用法 —— 必然失败： 
[SERVE] 启动被拒绝：非法端口 '--serve'（应为 0-65535 的整数）
根因 A
cli.py 只把 serve 置为布尔标志，从不把 --serve 从 args 里摘除；随后 bind = args[0] 取到的就是字面量 "--serve"，被当成端口去 int()。只有把 bind 写在前面（--cli 127.0.0.1:8792 --serve）才能侥幸工作。
现象 B
python -m gcm --help 不是帮助：__main__ 的 flags["cli"] 为假 → 落入 GUI 分支 → 创建 QApplication 并阻塞。实测 stdout 完全为空，stderr 只有一条 libpng 警告，进程挂了 43 分钟。对 agent / 脚本消费者而言，想查用法会得到一个挂死的图形界面进程。
修复
--serve 连值一起消费（del args[i:i+2]），缺值时报错并返回退出码 2；新增 _print_help()，并在 __main__.main 的所有分支之前拦截 --help / -h。
验证
--help 输出完整用法、rc=0；--cli --serve 127.0.0.1:8791 --json 真实阻塞在 serve_forever（timeout 返回 124 = 成功启动后被杀）；TestCliEntrypointContract 4 用例绿。

G66-12测试端口竞态 —— 间歇性红灯会训练人「重跑一次就好了」P1
怎么发现的
本轮提交后的验证阶段，同一条 99 用例命令第一次 ERROR: test_readonly_boundaries，第二次 OK。单独跑该文件也通过 —— 典型的顺序/时间相关，而非确定性缺陷。
根因
三个测试文件用 _free_port()「先 bind 到 0 拿端口、再 close、然后用这个端口」探测空闲端口。close 与真正 bind 之间有 TOCTOU 窗口，而同批有多个测试文件各自起 HTTP server，会抢端口。
为什么算 P1 而不是小事
间歇性红灯的真正危害不是这一次失败，而是它会训练维护者形成「重跑一次就好了」的习惯 —— 于是真正的回归被当成 flaky 忽略。测试基础设施的可靠性直接决定缺陷能不能被发现。
修复
三处改为 create_server("127.0.0.1:0") 由内核分配端口，再从 httpd.server_address[1] 反查真实端口 —— 端口从分配到使用之间没有空隙。顺带移除因此变为未使用的 import socket。
验证
同批 40 用例连跑 4 次全 OK（48s / 50s / 46s / 46s）。

这段文本经 autostart.py 拼进 任务计划操作失败（rc=…）：{detail} 直接展示给 UI 用户，不是内部细节。而且它是我自己在上一批「修复」里引入的 —— 说明修复本身也需要被审查。
根因（值得记住）
「统一 UTF-8」是经验规则，不是普适规则。Python 在 Windows 上通过 CreateProcess 调用控制台程序时使用 ANSI 代码页（GetACP()），而 Windows 自带工具普遍遵循这一点；git 是跨平台工具，自己输出 UTF-8。两者不是一回事。
修复
新增 _console_encoding()：取 locale.getpreferredencoding(False)（中文系统 = cp936，正是 ANSI 代码页），异常回退 mbcs；schtasks 两处改用它，git 等仍保持 utf-8。
验证
修复后实测 schtasks 错误文本恢复为可读中文；TestConsoleToolEncoding 3 用例绿（含真实调用 schtasks 断言不含 U+FFFD）；全仓编码分布复核 = 44 处 utf-8 + 3 处 schtasks 专用表达式。同时更新 CLAUDE.md 的编码规则（原规则写死了「一律 utf-8」，本身是错的）。

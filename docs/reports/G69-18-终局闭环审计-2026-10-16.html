G69-18 · 终局闭环总审计

Git-clone-Max · 基线 4459729（v9.3.2）→ 目标 v9.4.0 · 2026-10-16 · 报告生成者：主控代理 + 3 条并行只读审计线程
一句话结论： 项目里那份《下一步改进指南》被删掉时给出的理由是「全部闭环」—— 这个理由是错的。独立复验发现至少 6 项只做到一半、 3 项写了代码但从没接到产品里。更麻烦的是：CI 已经 连续 80+ 次红灯，而红灯的原因根本查不出来，因为 崩溃时它不打印任何失败用例名。本轮先把「看得见」这件事修好， 再修真实的断链。

一、这次到底在修什么（背景与直觉）

1.1 一个「看起来全好」的项目

这个项目的工程质量其实相当高：ruff 零告警、mypy 零错误、 121 个测试文件、1060 条快集用例在本机全绿。台账里 124 条任务全部标着 [✅ 已落地]，还有 ADR、SOP、发布清单、审计报告。

但同一天，GitHub Actions 上最近 12 次运行全部失败。 于是有了这次审计的核心直觉：

「本机全绿 + 台账全 ✅ + CI 全红」三者同时成立时，最可能出错的不是代码， 而是「我们用来判断对错的那些信号本身」。
测试可能绕过了真实路径；台账可能记录了「写了」而不是「通了」； CI 可能……根本没说清哪里错了。

二、关键判断是怎么做出来的

2.1 「本机绿、CI 红」不是 CI 在说谎

第一反应容易是「CI 环境有问题」。但本机是 Windows、CI 是 Linux/macOS， 直接断言「平台差异」是偷懒。真正有用的动作是制造一个对照实验： 把 HEAD 剥离成干净检出再跑一遍。 

git archive HEAD | tar -x -C /d/tmp/gcm_clean
cd /d/tmp/gcm_clean
QT_QPA_PLATFORM=offscreen <项目>/.venv/Scripts/python.exe \
  -m coverage run --source=gcm scripts/ci_run_fast.py

结果：FAILED (failures=3, skipped=4)。差异来源是工作区多了个 data/ 目录 —— 它让 get_data_dir() 走 legacy 回退分支， 改变了若干测试的行为路径。

而那 3 条失败全部是同一个机制：测试进程的父环境里本来就带着 GIT_CONFIG_*（CI 用 credential.interactive=false 就是这么设的）， 于是「断言 GIT_CONFIG_COUNT == 1」这类隐含「环境是空的」前提 的测试就红了。

2.2 顺手挖出一个真 bug

追这个环境问题时发现 GitService._env() 的实现有个更严重的问题： 

env = dict(os.environ)          # 把父进程的 GIT_CONFIG_* 一起抄了进来
...
env["GIT_CONFIG_COUNT"] = str(len(cfg))   # 然后从 0 开始覆盖
env["GIT_CONFIG_KEY_0"] = ...             # ← 把调用方自己的配置项吃掉了

git 的 GIT_CONFIG_KEY_<n> 协议要求索引从 0 连续。 原实现从 0 重写并把 COUNT 改小， 等于悄悄删掉了父进程设置的 git 配置。 这不是测试问题，是产品行为问题 —— 所以改成追加在既有项之后。

2.3 CI 为什么红了 80 多次却没人修

用 gh 拉下完整日志后，真相很朴素： unittest 的失败清单在进程崩溃时根本没打出来。 日志里只剩一串 ....F.... 的点阵和一句 Process completed with exit code 139。

一个不会告诉你哪里错了的门禁，等价于没有门禁。
80 次红灯没人修，不是因为大家不关心，而是因为无法行动。

所以本轮第一优先级的修复不是「修 bug」，而是把门禁变得可诊断。

3.1 独立审查线程抓到我自己写错的东西

按约定，修完必须由独立线程复验。它没客气 —— 抓到我引入的 3 个缺陷：

严重度我写错的后果
高 异常处理分支里调了 applog.debug()，而这个方法不存在 处理坏输入的分支自己会崩，中断所有 git 子进程调用 —— 比它要处理的坏输入严重得多
中 把 addCleanup 的 LIFO 顺序理解反了 注释声称的执行序和真实执行序不一致，每个用例白等 5 秒
中 声称 atexit 能兜住进程崩溃 真正的 SIGSEGV 下 atexit 根本不执行 —— 要靠 faulthandler
这三条本身就是本轮方法论的最好证据： 「修好了」和「没修坏」是两件事，必须由不写这段代码的一方来验。

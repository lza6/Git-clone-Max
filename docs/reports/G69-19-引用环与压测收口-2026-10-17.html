Git-clone-Max · v9.4.1 → v9.4.3 · 2026-10-17 · 主线程 + 对抗式审查线程 + 并发压测
一句话：上一轮把 CI 从「连续 80+ 次红灯」救回全绿，但用的是 关掉循环 GC 这种「绕过」。本轮去拆真正的雷 —— 为什么窗口必须等 GC 才能释放。顺带补全了 Webhook 的幂等/审计/重试， 并用并发压测抓出一个「40 个并发只该发 1 次、实际发了 13 次」的竞态。

本轮 5 个 bug 里有 4 个是我自己引入的。这不是自嘲，是这轮最有价值的事实。

一、先讲直觉：为什么「等 GC」会导致段错误

Python 释放对象有两条路：

路径触发时机时序可控吗
引用计数最后一个引用消失的那一刻 可控 你知道它什么时候发生
循环 GC解释器在任意内存分配点顺手做的一次扫描 不可控 可能正好在 processEvents() 内部

如果 MainWindow 被一个引用环维持，它就只能走第二条路。 而 Qt 的事件分发也是在一个循环里跑 —— 于是出现了最坏的组合： 

QApplication.processEvents()
  └─ 分发计时器事件
       └─ 此刻 Python 的循环 GC 恰好触发，销毁了 MainWindow 及其子定时器
            └─ 回到 Qt：QTimerInfoList::activateTimers 解引用**已释放**的定时器
                 └─ SIGSEGV
这解释了全部怪现象：
崩溃点随机漂移（取决于 GC 当时在哪）· PYTHONMALLOC=debug 会改变结果（分配模式变了）· 测试越多越容易崩（分配越多，GC 越频繁）· C 栈永远停在 activateTimers。

二、环到底长什么样（实测，不是猜）

用 gc.get_referrers + 遍历所有函数对象的 __closure__，把环的每一段都打印出来：

环的一段具体形态为什么成环
Panel ↔ 窗口 self.owner = owner（4 个 Panel） 窗口持有 Panel，Panel 又强引用窗口
控件 → lambda → 窗口 btn.clicked.connect(lambda: self.xxx()) 控件持有连接，连接持有闭包，闭包持有窗口，窗口又持有控件
扫描闭包AlertScanner(_scan_repos) 里的闭包捕获 self 扫描器被窗口持有，闭包又持有窗口
剪贴板回调watcher.on_url = self._on_clipboard_url 存的是绑定方法（强引用 self）
拖拽 handleredit.dragEnterEvent = self._repo_input_drag_enter 同「把绑定方法挂成控件属性」
关键洞察：PyQt 对绑定方法用弱引用，对 lambda 用强引用。
所以 connect(self.on_click) 天然不成环，而 connect(lambda: self.on_click()) 会。 这一条把「改造」变成了机械动作，不需要重构架构。

2.1 验证：只看一件事 —— del 之后有没有立刻释放

w = MainWindow(...)
gc.collect(); ref = weakref.ref(w)
del w
print(ref() is None)    # 修复前：False（还得等 GC）   修复后：True（引用计数立刻释放）

这一条比「跑一遍测试没崩」可靠得多 —— 它是**判定性**的，不靠运气。

三、Webhook：从「只会发一次」到可运维

能力之前现在
重复通知引擎重投/多批次收尾会把同一条通知发很多次 同 payload 600 秒内只发一次
排障「为什么没收到通知？」只能猜 <data>/notify.log 台账：发送/失败/被去重，含尝试次数
网络抖动失败就没了重试 1 次（短暂退避）
查看无设置页「查看通知审计」
这里我自己埋了一个凭据泄漏，被自己的实测抓住。
审计最初用 redact(url) 打码。但 redact 只按已知参数名 （token / api_key …）匹配，而 Webhook 的密钥常常在路径里： Server酱是 .../<KEY>.send、Telegram 是 /bot<TOKEN>/sendMessage， 或者干脆是自定义参数 ?k=SECRET。三种形态实测全部明文落盘。

改法：审计里只记 scheme://host，path 和 query 一律不落盘。 排障只需要知道「发往哪个服务」，不需要完整 URL。

四、压测：40 个并发，只该发 1 次

幂等这种东西，单线程测试永远是绿的 —— 必须压。

40 个线程 + threading.Barrier 同时起跑，同 payload 调 maybe_notify，网络 mock
期望：真正发送 1 次
实测（修复前）：13 次     ← 审计台账：sent=13 / dedup-skip=27

根因：去重是「先查后写」—— 锁只保护了查询，发送期间没有占位。 40 个线程几乎同时通过查重，然后各自发送。典型的 check-then-act。

# 修复前
with lock:
    if fp in recent: return          # ← 查完就放锁
sent = send(...)                     # ← 这期间别人也能通过查重
with lock:
    recent[fp] = now                 # ← 太晚了

# 修复后
with lock:
    if fp in recent: return
    recent[fp] = now                 # ← 查重与占位在同一次持锁内完成
sent = send(...)
if not sent:                         # 失败要撤销占位，否则「一次失败=整个窗口内再也不发」
    with lock:
        if recent.get(fp) == now: recent.pop(fp)

修复后实测：40 并发 → 发送 1 次，dedup-skip 39，审计 40 行全部合法 JSON。

写这条回归测试时第一次跑挂了，原因很值得记：
测试里漏了 import time，NameError 被 maybe_notify 的兜底 except 吞掉，表现为「发送成功但审计记 failed」。 兜底 except 是必要的，但它也会吃掉测试自身的错误 —— 所以测试必须能独立复现，不能只看被测函数的返回值。

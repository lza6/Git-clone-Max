### 0.2 证据标签（全文档强制）

每条结论必须落在四档之一，与 `policy.md` §3 一致：

- `已验证`：**本轮**或本文档编写轮实际运行并观察到结果（附命令与输出摘要）
- `静态确认`：读代码/文档确认，未运行
- `合理推断`：有间接证据，未直接验证
- `待验证`：缺环境 / 权限 / 凭证 / 时间

**「已验证」不接受转述**。执行方引用本文件的指标时，必须自己重跑一次再写进 `evidence/`。

### 0.3 状态回填规则（防止「全部完成」式伪闭环）

每个任务有唯一 ID（如 `S-03`）。执行完在**本文件对应条目的 `状态:` 行**改成：

```

```

**只允许** `TODO` / `DOING` / `DONE` / `CUT（附理由+拍板人）` / `BLOCKED（附最小缺失条件）` 五种。
禁止写成「基本完成」「已完成大部分」「理论上可行」。**没有 evidence 文件的一律不许标 DONE。**

## 2. 第一性原理：为什么是这三条主线

先把「用户到底买到了什么」说清楚，再谈改什么。

**这不只是一个下载器。用户买的是一句承诺：**

> 「我把 300 个仓库地址丢给它，它**正确地**、**可中断地**、**可解释地**落到我磁盘上，
> 并且**随时能告诉我它做了什么**。」

把这句话拆到底层，会得到 6 个不可约的约束，其中 3 个当前是结构性短板（对应用户选的三条主线）：

| # | 约束（第一性） | 现状 | 归属 |
|---|---------------|------|------|
| C1 | **不可逆性必须被消灭**：任何会动磁盘/删数据的动作，用户必须能先看见后果、事后能撤回 | ❌ 全库 `dry_run` / `batch_plan` / `oplog` **零命中**（本轮 grep 复测）；「开始」一按就是真克隆，「清理」一按就是真删 | **主线①安全网** |
| C2 | **时间是第一维度**：这个工具的真实用法是「挂着几周」，正确性必须按「第 200 小时」评估而不是「第 2 分钟」 | ⚠️ 有 WAL 收缩、事件环形缓冲、`mem_soak.py` 基线（500 轮 276 KiB / 2000 轮 280 KiB，**不随轮数增长**）；但**无长时真机 soak 证据**，句柄/子进程/定时器累积未见守卫 | **主线②稳定性** |
| C3 | **可解释性**：用户问「为什么这批慢 / 为什么这个失败」时，系统必须能当场回答，而不是让他翻 `app.log` | ⚠️ 已有分阶段耗时 `stage_json` + 错误分类 `action_kind`；但**没有「这条仓库的 git 命令历史」**（`GitCommandLog` 零命中） | **主线①/②交界** |
| C4 | **信任来自反馈**：每一次点击都必须有「我收到了 → 我在做 → 做完了/失败了」三态闭环 | ⚠️ v9.13/v9.14 已修 3 处典型（失败面板、大小列、诊断包/报表忙态），但**无系统性巡检**；「点了没反应」是历史上重复出现的缺陷类型 | **主线④UI 闭环** |
| C5 | **机器可验证 > 人肉记忆**：能靠守卫拦住的，不许靠文档提醒 | ✅ 这块很强（零断言/漂移/规模/接线/契约六类守卫齐备）；本次只需补 3 个新守卫入口 | 主线④附带 |
| C6 | **可被 agent 调用**（结构化契约） | ✅ 已有 CLI `--json` / MCP / HTTP / SSE / 6 技能包；缺口登记为 **v10.1 候选**（见 §8） | 本轮**不做**（用户拍板③） |

**为什么把「安全网」排在稳定性前面**（而不是按「越底层越先做」）：
C1 的缺失是**唯一会直接毁掉用户数据信任**的一类问题 —— 一次误删本地仓库、一次误 `--prune`，
用户就再也不挂机了。而 C2 的短板是**不确定**（缺证据），不是**已知会坏**。
先用一个版本把「不可逆」清零，再用同一批基础设施（plan 差异表 = 批量操作的统一入口）
去承载稳定性改造，比反过来便宜。

`合理推断`（这是排序判断，不是事实）

用户已拍板「一次性大版本」，所以 v10.0.0 内部按**可独立验收的 wave** 切，**顺序不可交错**：

```
W0  破窗（清基线）           →  B-0-1 / B-0-2 / B-0-3 / B-0-4(bump 脚本)
      gate: 卫生守卫绿 + 快集绿 + git status 干净
        │
W1  安全网（主线①）           →  P-xx（预览/dry-run）+ O-xx（oplog/撤销）+ G-xx（git 命令日志）+ R-xx（prune 三态）
      gate: dry-run 零写操作 E2E + 撤销往返 + 打码断言
        │
W2  稳定性（主线②）           →  S-xx（长跑/并发/失败路径/数据完整性）
      gate: 4 小时 soak 无增长 + 失败路径矩阵全绿
        │
W3  UI 闭环（主线④）          →  U-xx（反馈/空态/一致/DPI/可达）
      gate: 反馈巡检表逐条有断言 + 截图审计 4 主题×5 尺寸零裁切
        │
W4  收尾（治理）              →  G-xx（守卫/文档/版本/清理）
      gate: 全量 DoD（§10）
```

**为什么 W0 必须最先**：当前基线**已经不干净**（§1.2 四条）。在一个红着的基线上改引擎/UI，
后面任何一次「新引入的红灯」都无法归因 —— 这是本项目历史上反复付学费的地方。

### 3.2 依赖关系（谁阻塞谁）

```
W0-B-0-4 (bump_version.py) ──────────────┐
                                          ▼
W1-P (plan/dry-run) ──┬──> W1-O (oplog/撤销) ──> W1-R (prune 三态)
                      └──> W1-G (git 命令日志)   [独立，可并行]
W1-P 产出的「差异表」是 W2 与 W3 的共用底座（批量操作唯一入口）

W2-S 全部独立于 W3-U（不同文件），可与 W3 并行
W4 必须在 W1/W2/W3 收口后（版本 bump + 文档回填 + 清理）
```

**并行纪律**（`decisions.md` D-32 血的教训）：`main_window.py` / `settings_panel.py` 是**单点写者**，
同一时刻只允许一个执行者碰；并行只能用于**互不重叠的新文件**（如新模块 + 新测试 + 新脚本）。

### 3.3 v10.0.0 的「不算完成」清单（提前说清，防自欺）

- ❌ 不是「所有 §8 候选都做完」——§8 的项**故意**不进 v10.0.0。
- ❌ 不是「覆盖率数字提高」——覆盖率不是本版目标，**行为可验证**才是。
- ❌ 不是「重构变漂亮」——本版不拆 `main_window.py` / `service.py` / `engine.py`（§1.4）。
- ❌ 不是「UI 换皮」——本版只做**反馈闭环与状态一致性**，不动既定的视觉系统分层（`palettes`/`typography`/`qss_build`/`status_pill` 四层不回退）。

#### S-01 · 生产环境 `app.log` **从未生成**，28 处 `applog` 留痕全部丢进黑洞

**状态**: DONE（2026-11-08：`applog.set_default_log_path` + `__main__._init_applog` 唯一入口挂载；tests/test_s01_applog_default_path 5 例，真机 app.log 落盘验证）

- **证据（本轮我独立复现）**：
  ```bash
  ./.venv/Scripts/python.exe -c "from gcm.app import applog; lg=applog.get_logger(); print(lg.handlers); applog.info('probe'); print(lg.handlers)"
  # 输出：[]  /  []        ← 两条都是空
  ```
  代码层：`applog.py:41-71`（只有传 `log_path` 才挂 `RotatingFileHandler`）；
  `get_logger` 在 `applog.py` 之外**零调用点**（`grep -rn "get_logger" gcm/` 只命中 `applog.py` 自身）；
  `gcm/__main__.py:92-124` 只装了 `install_excepthook(data_dir/"error.log")`，**没有日志初始化**。
  `applog.(info|warn|error)(` 全库 **28 处**（`engine.py` 占 21 处），全部不传路径。`已验证`
- **失败场景**：500 仓批次里某条结果落库失败（磁盘满/DB 锁）→ `engine.py:1353` 的 `applog.error` →
  无 handler → 静默丢弃。用户按提示打开 `data/app.log`，文件**根本不存在**；
  `diag_bundle.py:150` 打包出的 `app.log` 永远为空 → 诊断包里「最近发生了什么」这一栏是假的。
  同理丢失的还有：「并发已自动降至 4」「疑似卡死」「FTS 重建失败」「重投失败」……
- **根因**：单例 logger 的 handler 挂载权交给了「调用方传路径」，而真正需要留痕的 28 处全都不传。
  另：`info/warn/error` 外层 `except Exception: pass`（`applog.py:74-90`）把所有写日志失败也吞了。
- **落地**：
  1. `applog.py` 增进程级默认路径：`set_default_log_path(path)`，`get_logger(None)` 时用它（仍保持 `reset_for_tests()`）。
  2. `gcm/__main__.py` 拿到 `data_dir` 后**第一件事**就是 `applog.set_default_log_path(data_dir / "app.log")`
     （要早于 `Database(...)` 构造，否则开库期的日志同样丢）。
  3. **不要**去 28 个调用点各补一个参数（会再漏）—— 这正是 `decisions.md` D-39「同一映射只留一份」的应用。
  4. 顺带把 `except Exception: pass` 改成「失败时退化到 `sys.stderr` 一次」而不是静默（避免二次踩坑）。
- **禁区**：不许绕过 `applog` 直接 `open()` 写日志（打码在 Formatter 层，见 S-11）。
- **验收**：
  1. `python -c "...; print(applog.get_logger().handlers)"` → 非空（≥1 个 `RotatingFileHandler`）。
  2. 跑一次 `QT_QPA_PLATFORM=offscreen ./.venv/Scripts/python.exe -m gcm --cli --json <临时url文件>` →
     `%APPDATA%/.../app.log`（或便携模式 data 目录）存在且含启动行。
  3. **守卫**（新增，先红后绿）：启动生产入口后断言 `get_logger().handlers` 非空 +
     `grep` 断言「`applog.` 调用点数量 == 28±N 且无一处传自定义路径」或干脆断言
     「`applog.py` 之外不再出现 `logging.getLogger`」。
- **工作量**：S（2~3 小时 + 测试）
- **风险**：日志路径在便携模式/安装模式下不同 → 必须走 `get_data_dir()`（S10 接缝：数据目录唯一来源）。

#### S-02 · 写库异常路径无 `rollback` + `_begin_immediate()` 吞错 → 半截写入被**下一次正常写一起提交**

**状态**: DONE（2026-11-08：6 个裸写方法迁 `write_txn`；tests/test_s02_write_txn 5 例含触发器注入失败 + 变异自检）

- **证据（审计实跑复现）**：
  ```
  A in_transaction: True                                   ← 写方法中途抛错后事务仍开着
  B 独立连接看到 multi.tags = ('PARTIAL-WRITE',)          ← 下一次正常 upsert 把它一起提交了
  ```
  代码：`repo_db.py:164-169` 的 `_begin_immediate()` 把**所有** `OperationalError` 都 `pass` 掉；
  无 rollback 的写方法清单（`静态确认`，执行前逐条复核行号）：
  `repo_db.py:277` `set_tags` · `297` `set_favorite` · `304` `set_note` · `313` `set_excluded` ·
  `511` `delete_repo`/`delete_all_repos` · `735` `import_metadata_json`；
  `repo_profile.py:51` · `repo_ssh.py:42` · `history_prune.py:75`。
- **失败场景**：`import_metadata_json` 第 2 条记录字段非法（或 DB 瞬时 `disk I/O error`）→ 抛错、事务悬挂 →
  紧接着引擎每条结果都要 `upsert_repo` + `add_sync_history`（`engine.py:1328-1340`）→
  其 `BEGIN IMMEDIATE` 报 `cannot start a transaction within a transaction` → 被 `_begin_immediate` **吞掉** →
  语句进入悬挂事务 → 后续 `commit()` 一次性提交**半截数据**。
  用户侧：从未导入成功的仓库出现在管理页；`delete_repo` 更糟（两条 DELETE 无事务）→ 只删历史不删仓库，留下孤儿行。
- **根因**：`gcm/db/txn.py` 的 `write_txn()`（v9.13.0 已为 `upsert_repo`/`add_sync_history`/`set_repo_head`
  修好）**没有推广**到同模块其余 6 处与另外 3 个 mixin；`_begin_immediate` 把「已在事务中」与「抢锁超时」当成同一件事。
- **落地**（**复用既有轮子，不新造**）：
  1. 上述 9 处全部改成 `with self._lock, write_txn(self):`。
  2. `_begin_immediate()` 只吞 `"cannot start a transaction within a transaction"`，且**先 `rollback()` 再重试一次 BEGIN**；
     其余 `OperationalError`（含 `database is locked`、`disk I/O error`）**上抛**。
  3. `txn.py` 的 rollback 失败分支升级为「标记连接失效 + 重建连接」（否则悬挂事务会一直存在）。
- **验收**：新增 `tests/test_db_write_txn_rollback.py`：对**每一个**写方法注入失败后
  ① 断言 `db._conn.in_transaction is False`；② 用**独立 `sqlite3.connect`** 读磁盘断言看不到半截数据。
  回归 `tests.test_c3_data` · `tests.test_g47_insights`。
- **工作量**：M（半天~1 天）
- **风险**：`write_txn` 与原 `_lock` 嵌套顺序若不一致会死锁 → 统一「先 `_lock` 后事务」并写进 `txn.py` docstring。

#### S-03 · schema 迁移失败被「强推版本号」固化为已完成 → **半迁移库永久不可自愈**

**状态**: DONE（2026-11-08：异常收敛到 v8 专属降级、其余上抛、user_version 分段成功后写；tests/test_s03_migration_atomic 3 例含中途失败重跑验证）

- **证据（审计注入失败复现）**：`repo_db.py:137-147`
  ```python
  try: _migrate(self._conn)
  except sqlite3.OperationalError:      # 本意只想给 v8 建 FTS5 虚表降级
      self._conn.rollback()
      ...
      self._conn.execute(f"PRAGMA user_version={_SCHEMA_VERSION}")   # ← 强行推到头
  ```
- **失败场景**：首次开库时磁盘满/锁超时 → 迁移中断，但 `user_version` 被写成 8 → **之后每次打开都跳过迁移**，
  `dir_stats` 表永久缺失，`set_dir_sizes` 报 `no such table`；且 SQLite legacy 事务模式下 DDL 走 autocommit，
  `:141` 的 `rollback()` **撤不掉已执行的 `ALTER TABLE`** → 「改了一半的 schema + 版本号已封顶」= 永久坏库。
- **根因**：降级粒度搞错 —— 只有 v8 允许降级，却把**整个** `_migrate` 包在一个 `except OperationalError` 里。
- **落地**：`_migrate` 内部**只**对 `migrate_to_v8`（建 FTS 虚表）单独 try/except 降级（FTS 不可用是可接受的降级，
  `known-issues` 已有「SQLite 不带 FTS5 时应用仍可用」的既有语义）；其余异常**上抛**，
  且 `PRAGMA user_version` **只在迁移成功后**写；`Database.__init__` 对迁移失败给可操作提示（不是裸 traceback）。
- **验收**：新增 `tests/test_db_migration_atomic.py`：注入 `database or disk is full` 失败后断言
  ① `PRAGMA user_version < 8`；② 重开库会**重跑**迁移；③ 最终表存在。
- **工作量**：S（2~4 小时）
- **风险**：这是 **T3 高风险**（DB 迁移，`policy.md` §2）→ 必须先出「影响分析 + 回滚方案」，
  并在 W1 的 oplog v9 迁移（O-01）**之前**修好，否则 v9 迁移会踩同一个坑。

#### S-05 · `url_lib` 用 `sanitize_name` 污染了**网络 URL** → 静默克隆到**另一个仓库**／404／目录撞车

**状态**: DONE（2026-11-08：URL 语义与目录名解耦 —— URL 保原始段、folder_name 才清洗；tests/test_s05_url_semantics 4 例）

- **证据（我本轮实跑）**：
  ```bash
  ./.venv/Scripts/python.exe -c "from gcm.app.url_lib import parse_any_repo_url as p; print(p('https://github.com/foo/.github').url_https)"
  # → https://github.com/foo/github.git      ← 少了点，指向另一个仓库
  ```
  `https://github.com/foo/CON` → `https://github.com/foo/CON_.git`（必 404）；
  `https://gitlab.com/group/sub/src/myrepo.git` → 子组被动作段剥离规则截断；
  `github.com/a/b__c` 与 `github.com/a__b/c` → `folder_name` 撞车（同一目录两个仓库）。
  代码：`url_lib.py:340-347`（`sanitize_name(owner)` / `sanitize_name(repo)` 后**重新拼 `url_https`**）。
- **失败场景**：`github.com/foo/.github`（真实常用仓）被改写成 `foo/github` → 静默克隆同 owner 下**另一个仓库**，
  或 404 后报「仓库不存在」；企业 GitLab 子组名恰好是 `src`/`wiki`/`tags` 时克隆父级路径；
  撞车时后到者被判 `platform`（「平台或文件路径限制」），提示与真实原因无关。
- **根因**：`sanitize_name` 的职责是「生成安全的**本地目录名**」，被误用于**网络标识符**；
  GitHub 专用的「动作段剥离」规则被无条件施加到所有 host 的深路径；`folder_name` 用 `owner__repo` 裸拼无唯一化。
- **落地**：①`url_https` 用原始 `segments[-2:]`（只剥 `.git`），`sanitize_name` **只**喂 `folder`；
  ②动作段剥离仅在 `len(segments)==3` 或 `host=="github.com"` 时生效；③`folder_name` 冲突时追加稳定短 hash；
  ④`ref` 段也过 `sanitize_name`（`@v1<2` 会让 `mkdir` 直接失败）。
- **验收**：新参数化用例（至少 8 个 URL 形态：`.github` / `CON` / 子组 / 深路径 / `@ref` 含非法字符 / 撞车对照）；
  回归 `tests.test_c1_wiring` · `tests.test_core`（含 `url_lib` 既有用例）。
- **工作量**：M（半天）
- **风险**：改 `url_https` 会影响 `repos.url_https` 落库与去重键 → **必须**核对 `UNIQUE(owner,repo,host)` 与
  `test_g67_closure` 的 host 污染用例；已落库的旧数据不回填（保持原值，只保证新解析正确）。

#### S-08 · `_on_result` 在 GUI 线程串行做「跨进程锁 + fsync + SQLite 写」——实测 **38ms/仓**

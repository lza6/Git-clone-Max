
## 9. 每个节点的统一作业契约（执行方必读）

### 9.1 节点作业模板

每个任务 ID 执行时按这个七段走，不许跳：

1. **开工核现状**：`git status --porcelain`（必须干净，见 §3.1 W0）+ `bd ready` +
   `git grep -n "<要用的符号>"` 确认它当前**真的不存在**（本文件的「零命中」结论是 2026-11-04 的快照，
   执行那天可能已变）。
2. **写失败测试（RED）**：先写会红的测试并**跑一次确认它红**，把红的原因（不是语法错）记进 evidence。
3. **最小实现（GREEN）**：只做让测试变绿的最小改动，不夹带重构。
4. **定向回归**：跑该改动点**既有**的测试文件（清单见各任务「验收」与 `test_ledger.md` 对应接缝）。
5. **反向自检（变异）**：故意把实现改坏一处 → 该测试必须红 → 改回来。**这一步不许省**（`decisions.md` D-27）。
6. **收尾门禁**：`ruff check gcm` + `mypy gcm` + `doc_drift_check.py`。
7. **落证据**：`evidence/<批>.json`（命令 + 退出码 + 输出尾部）+ `docs/验证记录-<日期>.md` 一节 +
   `changelog.d/` 一条碎片 + 本文件该条目的 `状态:` 行。

### 9.2 证据纪律（本项目翻过 3 次车的地方）

- **`*.log` 不能作为唯一证据**（`decisions.md` **D-31**）：跑过一次的绿色**必须**落进 `evidence/*.json`
  或 `docs/验证记录-*.md`，否则事后无法复核 = 等效于没跑。
- **本地绿 ≠ 干净检出绿**（`D-30`）：凡是断言「仓库状态」的守卫（索引、文件集合、行数），以 CI 为准。
- **「只读」是提示词约束，不是权限约束**（`D-32`）：并行只读代理曾静默删掉 16 个被跟踪文档。
  → 需要并行时**串行**或**隔离工作树**；任何 `git add` 前先看 `git status --porcelain`。
- **过期结论必须连带清理**（`D-31` 第②条）：修好一个结论时，同一次提交里全仓 grep 该结论的派生引用
  （文档/计划/排期）一起更新 —— 否则「一条过期结论派生出一整轮无效工作」（v9.13 排期就是这么浪费的）。

### 9.3 契约纪律（只增不改）

任何对外契约（`--json` schema / MCP 工具入参 / HTTP 端点 / 退出码）本版**只允许新增可选字段与可选参数**：

- 新增字段必须可选（有默认值），旧消费方零改动可继续工作。
- 删除/重命名字段 = **破坏性变更** → 必须 bump `schema.version` 的**主版本**并在
  `docs/agent-contract.md` 写迁移说明，且要用户拍板（`policy.md` §3.1 第 6 条）。
- 退出码语义不变：`0` 成功 / `1` 失败 / `2` 用法或输入错误 / `3` MCP 未启用。
- 改完必须 `python scripts/export_contract.py --check` → 0。

### 9.4 并行纪律

| 可以并行 | 必须串行 |
|---------|---------|
| 互不重叠的**新文件**（新模块 / 新测试 / 新脚本） | 同一文件的多处修改（`main_window.py` / `settings_panel.py` / `engine.py` / `service.py`）|
| 读代码调研 | 「先定接口，后各自实现」的任何情况 |
| 不同 wave 的验收脚本 | 版本 bump、迁移链、契约 schema |

### 9.5 硬禁区（违反即判伪闭环）

- 拆 `main_window.py` / `service.py` / `engine.py`（§1.4）
- 把 SQL 写到 `gcm/db/` 之外（G80-B6 红线）；把 `"git"` 子进程写到 `gcm/git/` 之外
- `subprocess` 文本模式不给 `encoding`（git→utf-8；Windows 控制台工具→`_console_encoding()`）
- 出站文本不过 `redact`（UI / 日志 / agent 输出 / oplog / 诊断包）
- 新增设置项只写不读、或只读不写（S06/S41 接缝）
- 新增模块/函数只在测试里出现（零生产调用点 = 虚伪实现，`TestG69_18WiringClosure`）
- 为绿灯删测试 / 削弱断言 / 跳过用例 / 把静态检查说成真实路径验证
- 用字符符号表达状态（✓✕⚠ 在微软雅黑缺字形 → tofu，`D-22`）
- 新增 `.sh` 脚本（Windows 规则）；`subprocess` 里写死 `utf-8` 解 Windows 控制台工具

### 9.6 提交纪律

- 提交信息 `<type>: <description>`（feat/fix/refactor/docs/test/chore/perf/ci），**一个节点一个提交**。
- **不自动 commit / push / 发 PR**，除非用户本轮明确要求（本项目当前授权：**仅文档**）。
- 发版前 `git status --porcelain` 必须为空；`git ls-tree -r HEAD --name-only` 复核**提交树**（D-29）。

## 11. 风险、未验证项、留给你的后续拍板

### 11.1 本版最大的三个风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| **R-01 prune 删错数据** | 唯一「真删」功能；一旦删掉用户没提交的改动，不可挽回 | 三重护栏（`protected` 永不删 / 预览勾选 / oplog 记不可逆）+ T3 流程 + 独立审查 + 反向自检用例 |
| **O-01 迁移到 schema v9 回滚** | 一旦用户升级到 v10 再降级，旧版对 `user_version=9` 的行为未实测 | 执行时用「旧版代码 + v9 库」真跑一次并记录；必要时让旧版忽略未知表（只加表不动列，天然兼容）|
| **W2/W3 并行撞文件** | `main_window.py` 2877 行是单点写者 | §9.4 并行纪律 + 一动就提交 |

### 11.2 本文件里属于「待验证」的结论（执行时先复测）

- `grep` 零命中的四个能力（`dry_run` / `batch_plan` / `oplog` / `GitCommandLog` / `prune_untouched`）
  —— 结论基于 2026-11-04 的 `main@b705df1`。
- 旧版代码对 `user_version=9` 的兼容行为（§4 O-01）。
- `redact` 是否覆盖 `-c http.extraHeader=Authorization: …`（§4 G-01）。
- 报告中的 19 个超 100 行函数中，有几个会在本版被改动到（改动即须顺手拆小，`CLAUDE.md` §6 增量约束）。
- 四项 Windows 特有验证（125%/150% 真机 DPI、慢网长时挂机、UNC 路径、非管理员权限安装）
  —— 历史上每轮都只能标「未验证」，本版若无真机仍标未验证，**不许写成已通过**。

### 11.3 需要你（用户）在执行期拍板的事（执行方遇到时停下来问，不要自己定）

1. **oplog 保留期**：建议 90 天（随批次收尾清理）。要不要更长/永久？（更长会让库变大，但审计更全）
2. **`--prune-untouched` 删目录的方式**：`shutil.rmtree`（快、不可恢复）vs 移到回收站式备份目录（安全、占盘）
   —— 建议默认备份，7 天后自动清。
3. **UI 是否暴露 `--prune`**：本文件按「暴露但三重护栏」写。若你希望 v10.0.0 只在 CLI 暴露，删掉 P-02 的
   prune 勾选分支即可（工作量 -0.5 天）。
4. **v10.0.0 是否接受「不改 `--json` 主版本号」**：本文件按「只增可选字段、schema 主版本不变」写。
   若你希望彻底重构 CLI 输出，那是另一个量级的工作（需要 agent 契约迁移说明 + 用户侧脚本改造）。

来自 W2（稳定性审计）需你拍板的 5 条 —— **都属产品语义，不是缺陷判断**：

5. **单仓最坏时长是否要默认设上限**（对应 S-14）：现在 `time_budget_min=0`（不限），
   大仓满量克隆 + 多层降级 + 子模块可到 ~90 分钟/仓。
   (a) 默认 30 分钟上限，超时明确报「已用尽预算」（可能中断超大仓库首次克隆）；
   (b) 保持 0，但设置页把该控件标红提示（保留「挂机上不封顶」语义）。
6. **定时队列「窗内」语义**（对应 S-06）：(a) 每个时间窗/每天**只跑一次**（推荐，等于「每天同步一次」）；
   (b) 窗内发现上一批已完成就再跑一次（= 窗口期内持续追新）。这决定 S-06 的修法方向。
7. **关窗行为**（对应 S-17）：(a) 最多 3s 优雅等待后直接退出（可能有半写目录，下次预检会清理）；
   (b) 保持 12s 但加「正在停止…」提示；(c) 收尾搬到独立进程、主窗立即退出。
   三者对「会不会破坏用户数据」的风险不同。
8. **标签分隔符统一方向**（对应 S-04）：以 `|` 为准（只改读侧代码，**零数据迁移**，推荐）vs 以 `,` 为准
   （需一次性改库内已有 `tags` 列，改完对第三方导出更通用）。
9. **`event_sink` 二选一**（对应 S-16）：删除模块并修正文档（承认「事件不持久」），
   还是接线成真正的跨重启审计（要一并解决 10Hz 进度事件的体积问题 + 后台写）。

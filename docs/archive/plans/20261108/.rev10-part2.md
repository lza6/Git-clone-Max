
## 4. W1 · 安全网与可撤销（主线①，v10.0.0 的最高价值）

### 4.0 这批要解决的第一性问题

当前所有破坏性动作都是**一次点击 = 一次真实写盘**，且**事后无法回退**。这不是「缺个 dry-run 参数」，
而是三条链同时缺失（本轮 grep 全部零命中，`已验证`）：

```
grep -rln "dry_run\|batch_plan" gcm/   → 0
grep -rln "oplog"               gcm/   → 0
grep -rln "GitCommandLog\|git_command_log" gcm/ → 0
grep -rln "prune_untouched"     gcm/   → 0
```

**目标状态**：任何批量动作在写盘前都有一份**可审阅的差异**（哪几个会克隆 / 更新 / 跳过 / 删除，各自原因），
执行后有一个**只追加的操作台账**，能让用户对**可逆动作**一键撤回；而每一条 git 子进程都能在 UI 里回看。

**这批不许做的事**：不许重写 `engine.py` 的调度核心（T-41 已放弃）；不许改变既有 `--json` 字段语义
（只能**新增**字段，见 §9.3 契约纪律）；不许给「不可逆动作」假装能撤销（`git clean` / 删目录 只记录不承诺）。

### P-01 · 批次计划纯函数 `app/batch_plan.py`（**最关键的一块**）

**状态**: DONE（v9.18.0 G84-B5：`gcm/app/batch_plan.py` + CLI `--dry-run` + MCP `dry_run`，tests/test_g84_batch_plan 11 例）

- **目标**：把「这批要干什么」从 `engine.launch` 里的隐式行为，变成一个**纯函数返回值**。
- **证据（现状）**：`grep -rln "batch_plan" gcm/` **零命中** `已验证`。
  现状下「哪些仓库会被跳过/覆盖/更新」只有跑起来才知道，逻辑散在
  `engine._start_worker` / `service.sync` 的预检分支里。
- **根因**：没有「计划」这一层抽象。执行与决策耦合在 worker 内部，导致
  ①无法预览 ②无法给 agent 一份机器可读的意图 ③无法做 oplog 的 before/after。
- **落地规格**：
  - 新模块 `gcm/app/batch_plan.py`（**纯函数，零 I/O、零 Qt、零 DB 连接**，只接受入参）：
    ```python
    @dataclass(frozen=True)
    class PlanItem:
        spec: RepoSpec                 # 来自 app/url_lib
        action: Literal["clone", "update", "skip", "blocked", "prune"]
        reason: str                    # 稳定英文码：exists_clean / exists_dirty / not_a_repo /
                                       #   behind / up_to_date / remote_gone / local_modified / ...
        local_path: str                # 计划落点（engine 用的同一套命名规则，不要另写一份）
        est_bytes: int | None          # 拿不到就 None，不许编
        protected: bool                # True = 本地有未提交改动/未跟踪文件 → 永不覆盖/永不删
        dirty_reasons: tuple[str, ...] # 保护原因（给 UI tooltip）

    def build_plan(specs, *, local_state, options) -> BatchPlan:
        """local_state 由调用方注入（引擎/CLI/MCP 各自取），本函数只做判定。"""
    ```
  - **目录名规则唯一来源**：必须复用引擎现有的落点计算（`grep -n "folder_name\|sanitize_name" gcm/app/engine.py gcm/git/service.py`
    定位后抽成共用的纯函数，或直接调用现成实现）——**不许在 `batch_plan.py` 里手抄第二份命名逻辑**
    （这是 `decisions.md` D-39「同一映射只允许一份实现」的直接应用）。
  - `local_state` 由 `db/repo_db`（是否已登记 + `local_path` + `head_sha` + `last_sync`）与
    文件系统探测（目录存在？是不是 git 仓？`git status --porcelain` 是否非空）合成；
    **文件系统探测放在调用方**，`build_plan` 只吃结果，保证可单测。
  - 判定优先级（**写进函数 docstring，测试逐条钉死**）：
    `blocked（目标路径存在但不是 git 仓）` > `protected（本地有改动）` > `update（已登记且有上游）`
    > `skip（up_to_date）` > `clone（不存在）`；`prune` 只在显式 `--prune` 模式下产生。
- **禁区**：
  - 不许在纯函数里读 settings / 连 DB / 读文件系统（否则无法测「3000 仓计划」的耗时）。
  - 不许新增设置项来「开关预览」（预览不是偏好，是强制路径）。
- **验收**（缺一不可）：
  1. 单测（新建 `tests/test_b*_batch_plan.py`，默认落 CI 快集）覆盖 8 种判定：
     空批次 / 全新克隆 / 目录已存在但是 git 仓且干净 / 有未提交改动 → `protected` /
     目录存在但非 git 仓 → `blocked` / 上游删除 → `prune` 候选 / `up_to_date` → `skip` / 同一 URL 重复 → 去重。
  2. **性能断言**：3000 个 spec 的 `build_plan` 耗时 < 50ms（用 `time.perf_counter` 直接断言，
     参考 `scripts/bench_scale.py` 的既有基线口径）。
  3. 变异自检：把判定顺序里任一条前提改错（如把 `protected` 挪到 `update` 之后），测试必须红。
- **工作量**：M（半天~1 天，含测试）
- **风险 / 回滚**：纯新增模块，零调用点时对生产无影响；风险全部集中在「命名规则抄了第二份」→ 用
  「两处结果必须相等」的对照测试钉死（拿引擎现有函数与新模块对同一批 spec 输出比较）。

      id        INTEGER PRIMARY KEY AUTOINCREMENT,
      ts        TEXT NOT NULL,              -- ISO8601 本地时间
      action    TEXT NOT NULL,              -- 稳定英文码：repo_delete / repo_delete_all /

### R-01 · `prune` 三态（`--prune` / `--prune-untouched` / `--no-clean`）

**状态**: TODO（2026-11-08 复核：未开工；L3 需 schema 批准）

- **目标**：远端已删除的仓库，用户能**安全地**清理本地痕迹；默认什么都不删。
- **证据（现状）**：`grep -rln "prune_untouched" gcm/` 零命中；远端删库后本地永久残留 `已验证`。
- **落地规格**：
  - 前置：**必须**先有 P-01 + O-01（prune 是 `build_plan` 的一种 action + oplog 必须记一条）。
  - 语义（写进 `docs/agent-contract.md` 与 `--help`，三种模式互斥）：
    | 模式 | 删 DB 记录 | 删本地目录 | 前提 |
    |------|-----------|-----------|------|
    | `--no-clean`（默认） | 否 | 否 | 只报告 |
    | `--prune` | 是 | **否** | 仅 `remote_gone` |
    | `--prune-untouched` | 是 | 是（进回收站式备份或 `shutil.rmtree`） | 仅 `remote_gone` **且** `protected=False` **且** 用户在预览里勾选 |
  - **三重护栏**：`protected=True` 的仓库**任何模式下都不得删除**；删除前必须走 P-02 的预览勾选；
    删除动作写 oplog（`undoable=0`，并在 UI 明确写「不可撤销」）。
- **验收**：
  1. 三态语义矩阵测试（3 模式 × 3 类仓库 = 9 例，断言 DB 行数与目录存在性）。
  2. 「本地有改动」仓库在 `--prune-untouched` 下**不被删**（这是最危险的一条，必须有反向自检）。
  3. CLI `--json` 输出含 `pruned` / `skipped_protected` 计数。
- **工作量**：M
- **风险**：**最高**。这是本版唯一「会真的删用户数据」的功能 → 必须 T3 流程（影响分析 + 回滚方案 + 独立审查）。

## 1. 执行纪律（给执行方的硬约束）

> 摘自 `policy.md`、`.agent/rules.md` 与 CLAUDE.md，**冲突时：安全边界 > 用户本轮目标 > policy.md > CLAUDE.md**。
> 上一份指南（Rev18）§1 的全部条款继续有效，此处只列最容易违反的几条 + 本轮新增。

1. **证据门禁**：任何「完成/通过/已修复」必须附本轮真实执行的命令 + 退出码 + 输出尾部。未运行 = 未完成。证据落 `evidence/rev20-*.json`。
2. **禁止过门禁手法**：删/跳测试、削弱断言、mock 生产逻辑、静默吞异常、TODO 占位充实现、未运行就写「测试通过」——出现即判伪闭环。
3. **TDD**：业务逻辑先写失败测试（RED）→ 最小实现（GREEN）→ 重构。只对外部边界（网络/时钟/对话框/子进程）mock。
4. **增量约束（勿重构）**：不大幅重构任何文件。新增 UI 逻辑落独立模块（`main_window.py` 3597 行、`progress_table.py` 808 行均已登记超限，**只减不增**）；新模块 200–400 行、硬上限 800；函数 ≤50 行、嵌套 ≤4 层。
5. **兼容扩展优先**：改已有函数优先加带默认值的参数（参考 G85 `before_retry` 范式）；`SyncResult`/事件/CLI JSON 只允许**加性字段**。
6. **子进程编码铁律**：`subprocess.run(..., text=True)` 必须显式 `encoding`；git 用 `utf-8`，Windows 控制台工具用 `_console_encoding()`。有 AST 守卫（`tests.test_g66_patch`）。
7. **脱敏**：出站文本（UI/日志/agent/事件）过 `gcm/util/redact.redact`；事件在入总线前已打码。
8. **i18n**：用户可见新文案走 `tr()`，key 同时进 `gcm/i18n/zh.py` 与 `en.py`；棘轮基线只降不升。
9. **解释器**：一律 `./.venv/Scripts/python.exe`（裸 `python` 是系统 3.14 无依赖，历史 exit 127 假象根因）。
10. **Windows 陷阱**：本机无 `rg`/`find` PATH（用 grep/python）；中文输出加 `PYTHONIOENCODING=utf-8`；PowerShell 链接用 `; if($?) {}`。
11. **引用环铁则**：信号连接用绑定方法或 weakref，禁止 lambda 捕获 `self`（`TestG69_18NoMainWindowRefCycle` 会红）。
12. **每完成一个任务批**：更新 `test_ledger.md`（新接缝）+ `docs/验证记录-2026-11-XX-Rev20.md`（命令+真实输出）+ `changelog.d/` 碎片（`python scripts/changelog.py new --category ... --slug ... --title ... --verify ...`）。
13. **真机 vs offscreen**：几何/视觉守卫在 offscreen 只能做「常量消费守卫」强度；真机问题（多屏/DPI/读屏）不盲改，登记 beads 等硬件窗口。
14. **多会话并发**（本项目实测踩过）：写文件前重新 Read；发现文件被外部改动先查 `git status` 与其他会话，不要用内存旧副本整文件重写。当前工作区 `event_panel.py` 的未提交改动**属于在途工作**，动这个文件前先与该改动合并而不是覆盖。

### R20-1（P1）per-host 退避接入投放链路 —— 让「感知调度」真正生效

- **动机（现状证据）**：`gcm/app/adaptive.py` 的 `HostBackoffTable` 已有完整语义
  （`on_failure` 记 `streak` 与 `_until[host] = clock()+delay`、`on_success` 清零、`delay_for()` 只读查询），
  `engine._on_result`（`gcm/app/engine.py:1443` 附近）也已按结果调 `on_failure/on_success`；
  但全库**没有任何地方读 `delay_for()`/`_until`** —— 同一 host 连续失败后，待发队列仍会立刻继续往该 host 投放。
  批次②的立项目标（beads `wlx`，已关）就是「per-host 自适应退避」，当前只完成了一半。
- **改法（最小闭环，不改并发模型）**：
  - 在 `engine._top_up_pending()`（`gcm/app/engine.py:359` 附近）投放循环里，对每个待投项先问
    `self._host_backoff.delay_for(host)`：若该 host 仍处退避窗口（`now < _until`，用 `time.monotonic()` 对齐组件内部时钟），
    则**跳过该条、保留在队列尾部**（不丢弃、不合成终态），继续尝试下一个不同 host 的条目；
    若整队都是同一退避 host，则本轮不投（下个 worker 完成或退避到期后自然恢复）。
  - 需要把「待发项的 host」带在队列元素上（`_pending_queue` 元组目前是 `(index, spec, flag)`，
    投放前可用现成 `self._host_for(spec)` 计算，**不必改元组结构**）。
  - 退避到期后的下一次 `_top_up_pending()` 自然恢复投放——无需额外定时器。
- **测试（先写，注入时钟）**：`tests/test_adaptive.py` 追加引擎级用例（或新建 `tests/test_r20_backoff_dispatch.py`）：
  ① 同 host 连续失败 2 次后，`_top_up_pending` 不再向该 host 投放新任务（断言 `engine.tasks` 数不增、pending 保留）；
  ② 推进注入时钟越过 `_until` 后恢复投放；③ 期间另一 host 的任务**照常投放**；④ 成功一次后该 host 立即恢复。
  注意用现有 `_make_engine`/stub service 模式，别起真网络。
- **风险与边界**：退避只影响「还没 start 的待发项」，绝不取消/终止在跑 worker（那是 cancel 语义）；
  `host_concurrency` 闸门逻辑保持不变（本条不与信号量交互）；
  `_host_backoff` 的 base=5s/max=300s 维持组件默认，不新增设置项（避免设置面膨胀；真需要再立任务）。
- **验收**：新增测试绿 + `tests.test_g43_engine`/`tests.test_core`/`tests.test_g52_engine_integration` 定向回归绿
  + `./.venv/Scripts/python.exe -m ruff check gcm` 与 `mypy gcm` 绿。

### R20-2（P1）慢 worker 判定接入可观测 —— `is_slow()` 有了消费点

- **动机**：`SlowWorkerMonitor.is_slow()`（中位数 0.3x 判据，floor 60s）当前零生产调用点；
  engine 只 `record` 耗时。批次②要的「慢 worker 健康检查」目前用户/agent 均不可见。
- **改法（刻意只做可观测，不改调度）**：在 `engine._on_result` 记录耗时之后，
  若 `self._slow_monitor.is_slow(folder_name, seconds)` 为真 → `applog.warn` 一条
  （含仓库名、本次耗时、中位数阈值），并 `self._publish(EventType.TASK_SLOW, key=..., elapsed_ms=..., median_ms=...)`。
  在 `gcm/app/event_bus.py::EventType` 新增 `TASK_SLOW = "task_slow"` 并加入 `ALL`
  （SSE/事件面板自动可见；`docs/agent-contract.md` §5.1 事件类型表同步补一行——该文档由 `doc_drift`/契约测试盯，别漏）。
- **为什么不做「降并发/踢队尾」**：批次②评审口径是「感知 + 退避」；把慢 worker 与调度决策耦合会显著放大回归面，
  且当前并发模型（QThreadPool + per-host 闸门）没有 worker 身份可踢。先用事件把「谁慢、多慢、阈值多少」暴露出来，
  观察真实批次数据后再决定是否需要动作类响应——这符合本项目「先可观测再自动化」的既有路径（S-08/卡死巡检同款）。
- **测试**：`tests/test_adaptive.py` 补引擎级用例：注入一批耗时使某仓库超过中位数 0.3x 阈值 → 断言发出 `task_slow` 事件且负载含 `elapsed_ms/median_ms`；正常耗时仓库不触发。
- **验收**：同 R20-1 的门禁；另跑 `tests.test_g71_event_stream`（事件面回归）。

### R20-3（P2）StopReason 进批次终态事件

- **动机**：批次⑤建的 `StopReason`（completed/cancelled/failed/exhausted，str 兼容）与
  `TASK_STATE_TO_STOP_REASON` 转换表目前只有测试消费；「这批为什么结束」仍要人从 counts 猜。
- **改法（最小）**：`engine._on_worker_done` 的批次收尾分支（`self.finished.emit()` 之前，现 `BATCH_FINISHED` 发布处）
  推导批次级 reason：`self._cancelled → CANCELLED`；否则 `counts.failed>0 且 counts.success==0 → FAILED`；否则 `COMPLETED`
  （`EXHAUSTED` 本版不判定——重试耗尽与失败的区分需要跨队列状态，留待真有消费方再加，不预造）。
  把 `stop_reason` 加进 `BATCH_FINISHED` 负载（加性字段）。`TASK_STATE_TO_STOP_REASON` 若最终仍无单任务消费点，
  按 vulture 纪律处理（接线或删除），**不要只为过门卫而留死代码**。
- **测试**：`tests/test_power_guard.py`（现有 StopReason 用例所在文件）补：取消批次 → `batch_finished` 事件 `stop_reason=="cancelled"`；全失败批 → `"failed"`；混合成功 → `"completed"`。
- **验收**：定向测试 + `tests.test_g71_event_stream` 回归。

### R20-4（P2）定时队列时间窗 UI + 队列删除

- **改法**：
  - `gcm/db/queue_db.py` 新增 `update_queue(queue_id, *, days, start, end, on_missed)`（复用 `parse_days/parse_hhmm` 校验与既有事务纪律）与 `delete_queue(queue_id)`（`BEGIN IMMEDIATE` + `DELETE`，写事务）。

  - 新文案全部走 `tr()`，zh/en 同步。
- **测试**：`tests/test_a14_queue_runner.py` 风格追加 DB 层用例（update 校验非法 hhmm 拒绝、delete 后 list 为空、delete 幂等）；

### R20-6（P3）`--diag` 的 GitHub API 限流/403 降级为 warn

- **动机（Rev19 §4.2/§5 实测）**：本机走代理（共享出口 IP）时 `api.github.com/zen` 返回 403 rate limit，
  `probe_github_api()`（`gcm/app/diag.py:32`）把它判成 `err` → 整体评级「红」，用户误以为工具坏了；
  实际克隆走 git 协议完全不受影响。
- **改法**：`probe_github_api()` 捕获 `urllib.error.HTTPError` 且 `code in (401, 403, 429)` 时返回
  `{"name": "GitHub API", "status": "warn", "detail": f"HTTP {code}（匿名限流/代理出口共享配额，环境性限制；不影响克隆，可忽略或配置 token）"}`。
  连接失败/TLS 错误**仍为 err**（那是真不可达）。`grade()` 逻辑不变（黄=有 warn 无 err）。
- **测试**：`tests/test_g54_ux.py` 已有 probe 系列用例，补：mock `urlopen` 抛 `HTTPError(url,403,...)` → `status=="warn"`；抛 `URLError` → 仍 `err`。
- **验收**：定向测试 + `tests.test_g49_cli.py::test_diag_*` 回归（CLI --json 的 `diag.grade` 口径不破坏）。

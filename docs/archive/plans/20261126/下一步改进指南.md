## 4. 方案对比与取舍

### 4.1 三个方案

**方案 1 — 防漂移收口（传统/维护向，v9.23.0 最小形态）**
修 I4（dev_metrics 单一来源化 + 反向自检守卫）、I5（CLAUDE.md 权威表加 `docs/plans/` 一行）、I2（发布清单增「真机人工验收（非阻塞）」节）。不新增产品功能，全部是让"下一位维护者不再踩同一坑"的动作。成本约 0.5 人日，风险极低，收益是审计噪音归零与流程闭环。

**方案 2 — agent 快速接入包（优化/生态向，叠加进 v9.23.0）**
补 `docs/agent-quickstart.md`：CLI `--json`、MCP stdio 握手（`GCM_MCP_ENABLE=1` + `clone_batch(dry_run)`）、HTTP SSE 三段五分钟可复跑教程，配 `scripts/realcalls_rev17.py` 同款证据脚本产出 `evidence/rev21-quickstart.json`。对齐 product-brief §4 方向 A（"生态接入"ROI 排第一，现状"部分"）。成本约 0.5–1 人日，风险低（纯文档+脚本，不动产品代码）。

**方案 3 — 产品型候选（创新向，待拍板，不进默认路线）**
两条互为替代的候选：**3a 知识索引导出**——把本地仓库库一键导出为带画像（`app/knowledge.py` 已有零 LLM 画像）的索引文件，供外部 agent/知识管理消费，补 product-brief 方向 C 的剩余缺口；**3b 无障碍工程化**——把 `scripts/a11y_audit.py` 升级为可访问性树导出 + 拔屏/触摸的半自动探针，压缩 `13k`/`cuz` 的人工窗口。两条都需要用户确认需求真实存在后才立项（3a 是新产品面，3b 是对已放弃"完美验收"倾向的再投入，二者都与既有决策有张力）。

### 4.2 权衡矩阵

| 维度 | 方案 1 | 方案 2 | 方案 3a | 方案 3b |

| 技术可行性 | 高（一行级+文档） | 高 | 中（新导出格式需定契约） | 中（Qt 可访问性 API 有平台差异） |

| 风险等级 | 低 | 低 | 中（需求未验证） | 中（与"已放弃事项"边界模糊） |
| 用户可观性 | 无（内部卫生） | 高（新用户上手路径） | 高（如果需求真实） | 低（少数硬件场景） |

### 4.3 推荐

**v9.23.0 = 方案 1 + 方案 2**（P21-1/2/3 + 发版 P21-4 + 归档 P21-5）。理由：全部低风险、可在一天内完成并发布；方案 1 是方案 2 的卫生前置（教程引用的数字/路径要过守卫）；方案 3 的两条都需要用户先回答"这个需求存在吗"，不替用户发明需求——这与本项目"不为未拍板项写实现"的纪律一致。若用户只想发 patch，§6.3 给出 `9.22.1` 降级口径。

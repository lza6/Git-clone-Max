## 3. 最强自我反驳与盲点扫描

> 先假定这份文档是错的，再逐条看能不能站住。

**R1｜「这份指南本身就是新的文档债」**
反驳：仓库已有 `workflow_status.md`（817 行、21 节历次台账）、`test_ledger.md`、`policy.md`、`.agent/memory/` 五件套；再加一份计划文档，只会让「哪一份是真的」更模糊 —— 而这正是 10-14 那次删 `计划书/` 的初衷。
回应：本文件**不复制**任何既存事实，只做两件事：① 把**未落地项**排成可验收的任务；② 把**证据指针**指向既存事实源。§1 的每个数字都带获取方式，§4 每条都带 file:line。真正防债的是 §17 + `docs/计划书/README.md` 的墓碑纪律：**闭环即归档删除**，不允许长期悬挂。
残余风险：若执行者只勾选不实现，本文件会变成第 N 份伪闭环证据 —— 所以 §8.3 强制「断言必须能失败」。

**R2｜「把 6 个设置字段说成 P1 是过度诊断」**
反驳：这些字段可能**故意**留给高级用户手改 `settings.json`（桌面工具的常见做法），补 UI 反而是加复杂度。
回应：分辨依据是「是否对外承诺过」。`post_clone_hook` 在 `README.md` 功能表之外被 changelog 登记为能力，`quick_repos` 在 `gcm/__init__.py` changelog 里写明「快捷填充可配置(quick_repos)」—— **承诺了却只能手改 JSON**，这是缺口而非特例。其余 4 个（`clone_timeout` / `minimize_to_tray` / `watchdog_silent` / `sched_report_format`）我**不主张**必须补 UI，标为「需用户决策：补 UI 或从 `Settings` 删除」。§4 已按此分档。

**R3｜「P0 无 = 项目没问题，这是自欺」**
反驳：本轮我没跑任何测试，「P0 无」只是历史证据的转述，`policy.md` §3 明确「已验证不接受转述」。
回应：接受。§4 P0 的标签写的是**历史证据 / 待验证**，不是「已验证」。要给 P0 结论定级，必须先跑 §11 的 E1–E4。

**R4｜「CI 阈值不一致是 bug」——可能误判**
反驳：`ci.yml:23` 的 84 可能是某次试验残留，也可能有 job 依赖它。
回应：已读全文 `test` job —— `:75` 步骤级 env 显式覆盖为 81/80，84 无任何消费点。判定为**死配置/误导值**（P3，不是 bug，不影响门禁）。但它在 review 时确实会误导人，故列入清单。

**R5｜「覆盖率 82% 已经是绿灯，再谈质量是数字游戏」**
反驳：门禁 81，实测 82，多 1 个点毫无意义；把精力放在百分比上是浪费。
回应：同意，本指南**不设**覆盖率提升目标。§9 验收矩阵里覆盖率的唯一要求是「不低于门禁」，增量要求全部是**行为断言**（能失败的断言），不是百分比。

**R6｜「不跑测试就写 P1/P2，是不是纸上作业」**
反驳：桌面 GUI 项目的很多「缺口」必须看真实渲染才算数（这正是 G74 的教训：测试只验控件存在，视觉问题全漏）。
回应：因此 §7 里凡涉及 UI 的任务都强制附带「截图审计 + 人工看关键图」（复用 `scripts/ui_screenshot_audit.py`），并在 §11 列为待执行项，而不是用离屏断言替代。

**R7｜「本地 API / SSE 无鉴权，是不是漏了安全项」**
反驳：agent 章节说只绑回环 + Host/Origin 校验，那 DNS rebinding 之外还有本地恶意进程可直连。
回应：这是**已披露的设计边界**（`docs/agent-contract.md` §5、`CLAUDE.md` §6「已知边界」），不是新发现的漏洞；本机同用户进程本就无法互相隔离。真正值得做的是「启用本地 API 时生成一次性 token」——但那会改公共契约，属 T3，需授权，故放 §5 方案 C，不在本轮动手。

**盲点（我主动补的，原要求未列）**
- B1：`docs/计划书/` 一旦建立，`tests/test_g67_docs_freshness.py` 会扫描其中的 `.md`，任何**写错或指向未来的路径**都会让 CI 变红（详见 §12 R-01）。这是本项目特有的约束，极易踩。
- B2：仓库根有 9 个调试日志/截图/空目录残留（§13），都已被 `.gitignore` 忽略，但会污染「干净检出对照」实验的前提。
- B3：`workflow_status.md` 已 817 行，继续追加会让检索成本指数上升 —— 建议每季度归档一次（§4 P2-11）。
- B4：`docs/architecture.md` §4 的行数表已漂移（§1.2），而它是「我该改哪」的权威入口。

## 5. 方案对比与权衡

### 方案 A｜接线收口（Recommended）
把已实现但用户够不到的能力一次性接到 UI 或明确删除：6 个设置字段、扫描进度、sha256 提示、数据目录入口、死信号。核心原则是「**要么接线，要么删掉，不留第三种状态**」。缺点是会动到设置页与主窗口两个高热区，需要成组的 UI 回归；但每个改动都小、可逆、有现成守卫范式（`tests/test_g69_regressions.py` 的 AST 扫描 + `tests/` 的控件契约测试）。收益是所有「文档说能做、用户做不到」的信任损耗一次性清零，且为后续任何功能开发建立「接线即验收」的肌肉记忆。约 1 个 minor 版本。

### 方案 B｜真机与 CI 硬化
把「离屏绿 ≠ 真机好」这个已知盲区制度化：每版必跑截图审计并人工看关键图（脚本 `scripts/ui_screenshot_audit.py` 已有），把 Windows 慢集与打包健康检查纳入流水线（`scripts/health_check.py` 已有），把 `e2e_smoke` 的覆盖从「克隆/更新」扩到「失败/取消/冲突」路径。缺点：CI 分钟数与人工时间成本上升，且慢集在 Windows 上可能引入新的 flake（历史上 `test_g67_closure` 在高负载下就偶发）。收益是把 G74 那种「只有人眼能发现」的问题从偶然变成常规。约 1 个 minor 版本。

### 方案 C｜agent 一等公民
把外部 agent 的使用体验当主路径：本地 API 启用时签发一次性 token（回环 + 鉴权，替代「裸奔但只绑回环」）、MCP 增加写工具（显式 `--allow-mutate`）、补齐 MCP `annotations`/`outputSchema`、提供事件文件桥让 `--serve` 也能看到 GUI 事件。缺点：全部是**公共契约变更**（T3），必须走影响分析 + 回滚 + 授权；token 一旦引入，所有既有 curl 示例失效。收益是打开 agent 生态的传播面（`docs/product-brief.md` §4 方向 A）。约 1 个 minor 版本，但必须先拿到授权。

### 方案 D｜产品增长（知识索引 / SaaS）
把「批量下载」升级成「批量理解」：克隆后生成 README 摘要、自动打标签、本地知识索引，再谈共享仓库池。缺点：引入 LLM 依赖与成本（触碰付费 API 红线）、索引质量不可控、与当前「单机零服务端」架构冲突。收益是唯一可能撑起商业模式的方向。成本高，建议只做**离线可用的最小切片**（本地全文索引 + 标签，不调外部 AI）。

### 方案 E｜工程治理（去文档通胀）
把文档与守卫的一致性交给机器：`docs/architecture.md` 行数表改成引用式、给 `docs/` 加「路径+版本」守卫的加强用例、拆分 `main_window.py` 的下一块、治理偶发用例。缺点是纯投入、无用户可见产出，容易被业务插队。收益是让后面每一次改动都更便宜，且直接消掉 §3-R1 的文档债。

### 5.1 评估矩阵（1–5 分，5 最好）

| 维度 | A 接线收口 | B 真机硬化 | C agent 一等公民 | D 产品增长 | E 工程治理 |
|------|-----------|-----------|-----------------|-----------|-----------|
| 技术可行性 | 5 | 4 | 3（改契约） | 2 | 5 |
| 开发成本（5=低） | 4 | 3 | 2 | 1 | 3 |
| 维护成本（5=低） | 5 | 3 | 3 | 2 | 4 |
| 性能影响 | 5 | 5 | 4 | 3 | 4 |
| 扩展性 | 4 | 3 | 5 | 4 | 4 |
| 风险等级（5=低） | 4 | 3 | 2 | 2 | 5 |
| 用户便捷性收益 | 5 | 3 | 3 | 4 | 1 |
| 可衍生性 | 3 | 3 | 5 | 5 | 3 |
| UI/UX 可观性 | 4 | 4 | 2 | 4 | 1 |
| SaaS 成熟度 | 2 | 2 | 4 | 5 | 2 |
| **合计** | **41** | **33** | **33** | **32** | **32** |

### 5.2 关键决策因素与推荐

1. **信任损耗是当前最大的隐性成本**：已有 11 处「实现了但够不到」（§1.3）。任何新功能开发前不先清这个，只会持续累加。
2. **A 与 E 互不冲突且共享验证手段**（都要跑定向回归 + 文档守卫），可同版本打包，摊薄发布成本。
3. **C 与 D 都需要**用户/商业决策**或**外部授权**（契约变更、外部 AI 成本），不应由执行者自行决定。
4. **B 的边际收益依赖 A**：A 完成后截图审计才有稳定的基线可比。

**推荐顺序：A（主）+ E（同版轻量），而后 B，C/D 待决策。** 具体见 §6。

## 15. 项目结构扫描结论与排除项

**扫描方式**：`os.walk` 深度 2 + 对关键目录做定点 `grep -rn`（Windows 下 `rg`/`find` 不在 PATH，见 `CLAUDE.md` §1）。

**结论（规模与分层）**：
- 入口 4 个：`gcm/__main__.py`（GUI）、`gcm/cli.py`、`gcm/mcp_server.py`、`gcm/http_api.py`。
- 分层清晰：`app/`（纯逻辑）→ `git/`（子进程封装）→ `db/`（持久化）→ `ui/`（PyQt6）；跨层工具在 `util/`。
- 规模：79 个 `.py` / 23,284 行；3 个文件超 800 行硬上限（§1.2），已登记为显式接受的技术债。
- 测试 133 文件，含真实 git 本地裸仓 E2E（`tests/test_core.py`）。
- 文档体系分三类：**事实源**（`docs/architecture.md`、`docs/agent-contract.md`、`docs/data-model.md`、`docs/adr/`）、**活 SOP**（`docs/RELEASE_CHECKLIST.md`、`docs/SOP-交付与维护.md`）、**历史证据**（`docs/验证记录-*.md`、`docs/reports/`、`evidence/`）。
- 治理文件：`policy.md`（交付门禁）、`test_ledger.md`（S01–S31 接缝）、`workflow_status.md`（轮次台账）、`.agent/memory/`（记忆五件套）。

**排除项（未读、不读）**：`.git/`、`.venv/`、`build/`、`dist/`、`__pycache__/`、`.mypy_cache/`、`.ruff_cache/`、`.coverage`、`data/`、`clones/`、根目录 `*.log`、`z.png`、二进制/压缩产物。
理由：无分析价值或体量过大；且 `data/` 属运行期状态，读它会污染「干净检出」判断。

**Aha（扫描中发现的、原要求未列的）**：
1. 项目**没有** `project_specs.md` / `db_structure.md`（用户提示词提到的两项）。等价物是 `workflow_status.md`（轮次台账）+ `docs/data-model.md`（数据模型权威）。按 `.agent/memory/decisions.md` D-07（`.agent/` 只放指针，权威内容不重复），**不建议**新建平行文件 —— 那会造成同一事实两份、必然漂移。本指南因此不创建这两份，改为在 §17 指路。
2. 根目录有 12 项调试/缓存残留（§13），说明本项目**没有**「提交前清场」习惯 —— 建议在 `docs/RELEASE_CHECKLIST.md` §0 加一条「根目录无调试残留」。
3. `docs/` 下的守卫只覆盖 `.md` 的**路径与版本**，不覆盖**行数/数量类陈述**（§1.2、P2-07 都是这类漂移）—— 这类数字最好的解法是「不写死数字」，见 T-08。

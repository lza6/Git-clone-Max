G79b 终局审计：把「闭环」的证据口径收紧

独立复验 G79 的全部交付，真跑了此前从没跑过的验收项（慢集绿灯、SSE 长连接、高 DPI、 变异实验、打包 exe 真实 E2E），抓出 3 处真实缺陷 —— 其中一处是入口文档与代码直接矛盾， 会指挥下一个 AI 做整整一轮无效工作。

1. 上下文：为什么会有这一轮

G79 按「工程治理收口」计划交付了 8 个任务，自称闭环。本轮不接受这个结论，做了两件事： 逐条复验（不信任何 ✅，用命令重新证明）与补齐验收面（§11 的 E1–E18 里有一半从未真跑）。

复验抓到的两处「证据折扣」

① 慢集绿灯没有持久化留档：evidence/G79-hygiene.json 写「129 OK / 68.9s」， 而仓库里唯一的 .g79_slow.log 是修复之前那次 FAILED (failures=1, errors=1) （AttributeError: 'Settings' object has no attribute 'depth'）。绿色那次跑过却没落盘 → 事后不可复核，等效于没跑。

② 过期结论没有连带清理：CLAUDE.md §6 在 9.4.5 移除 gc.disable 之后， 仍写着「整轮关闭自动循环 GC…仍未根治…要逐个改造 42 个构造 MainWindow 的测试文件」， 计划文档据此排了一个版本（v9.13）。

2. 直觉与取舍

一个「绿着的守卫」比一个「红着的 bug」更贵：bug 会被人撞到，失效的守卫会让人以为不存在。 所以本轮优先修的是断言与实现之间的缝，而不是加功能。

决定理由
修紧凑布局的孤儿按钮，而不是「把行整行隐藏」 整行隐藏会让小屏用户永久够不到快捷填充编辑入口（违反本项目「新增能力必须有 UI 入口」红线）；保留标签 + 固定宽度按钮，既省空间又不丢入口
扩守卫，而不是只改代码 原守卫只断言 quick_scroll.isHidden()，于是「只剩一个孤立的编辑按钮」也算绿。守卫要断言的是一条不变量（收起后仍可读、仍可用、不被拉伸），不是某个控件的某个布尔值
不做 T-41/T-42/T-43（主窗与设置模块拆分） 它们是重构（__init__ 233 行 / _launch 129 行 / settings_groups 783 行），按既定排期留 v9.11 / v9.12。本轮授权明确禁止大幅重构
撤销 T-44 / P2-9 而不是继续排期 前提已不成立（gc.disable 全库无、引用环已打断、1439 用例 0 崩溃）。继续排期 = 用过期结论制造无效工作

3. 做了什么

F1 · 紧凑布局「快捷填充」行退化（P2，代码 + 守卫）

窗口高 < 820px（1024×768 / 1366×768 / 1280×800）时，chip 滚动区被收起，但 G76 新增的「编辑」按钮 在滚动区之外不会隐藏，且被收起控件的伸缩空间轮到它 —— 实测被拉成 652 / 609 / 481px 的通栏按钮。 既不是 G74 注释自称的「整行隐藏」，也让人不知道在编辑什么。

layout_mode(w,h) ──compact──▶ _apply_layout_mode() ├─ hide: quick_scroll ← chip 区收起（设计如此） ├─ keep: quick_label ← 改：该行读作「快捷填充：」 └─ keep+Fixed: btn_edit_quick ← 改：自然宽度，不被拉伸 │ └─▶ 守卫 4 条不变量（1024×768 也纳入矩阵） + 两次变异实验：改回旧行为必须红

F2 · 同版本断言语义退化（P2，测试）

test_check_latest_no_exe_asset 把 3.0.0 写死并注释「= 当时的版本号」。 版本越过后它实际测的是「更旧版本不算更新」，同版本分支再没人覆盖，而断言仍绿（断言强度悄悄退化）。 改为按真实 __version__ 动态构造，语义回到注释所写。

F3 · CLAUDE.md §6 与代码直接矛盾（P1，文档）

改为「已根治（G79b 复核更正）」：保留历史根因与观测（复盘材料），补上现状 （弱引用 + 绑定方法，9.4.2–9.4.5）、守卫名与实测结论；明确「改造 42 个测试文件已不是待办」； 保留仍然有效的编码约束（信号连接不要用 lambda 捕获 self）。

7. 测验（自测通过率 100%，通过标准 ≥ 80%）

  1. 紧凑布局下，为什么不能简单地把「快捷填充」整行藏掉？
    答：G76 加在滚动区之外的「编辑」按钮是唯一的快捷填充编辑入口，整行藏掉会让高 <820px 的用户永久够不到该功能，违反「新增能力必须有 UI 入口」的红线。正解是保留标签 + 固定宽度按钮。
  2. 旧的 test_g78_quick_scroll 为什么绿着放过了缺陷？
    答：它只断言 quick_scroll.isHidden()，而缺陷的形态是「滚动区确实藏了，但同一行还剩一个无标签的孤立按钮，且被拉成通栏」。断言覆盖的是「某个控件的一个布尔值」，不是「这一行的可用性与可读性」这条不变量。
  3. 「变异实验」在这轮起了什么作用？给出两次实验的失败信息关键片段。
    答：证明新守卫能真失败（不是空转）。① 还原旧隐藏清单 → AssertionError: (1366,768) 紧凑模式下标签被藏掉 → 编辑按钮成了孤儿（failures=3）；② 删掉尺寸策略 → 652 not less than or equal to 64 : 被拉伸成 652px（1280×800 → 609px，1024×768 → 481px）。
  4. 为什么 3.0.0 这条断言「绿着但已经不再测它声称要测的东西」？
    答：注释写「= 当时的版本号」，但版本早已 > 3.0.0，于是 check_latest 比较的是「更旧版本 → 不是更新」，同版本分支（相等 ⇒ 不是更新）不再被任何用例覆盖。断言能过，是因为它测的是另一个分支。
  5. CLAUDE.md §6 那段的错误属于哪一类？为什么它比一个普通 bug 更贵？
    答：属于「过期结论未连带清理」。它是所有 AI 与新协作者的第一入口，会直接指挥下一轮去改造 42 个测试文件、并据此排出 v9.13 —— 一条过期结论派生出一整轮无效工作。
  6. 本项目判定「一个计划文档能不能删」的三个前提是什么？
    答：①逐条复验过；②无未闭环项；③无待决策项（policy.md §5）。三者同时成立才可归档删除；本轮 T-41/T-42/T-43 未开始 + P2-5/P2-8 未闭环 ⇒ 不可删。
  7. 慢集「留档缺口」是怎么发现的？正确的留档方式是什么？
    答：用 evidence/G79-hygiene.json 声称的「129 OK」去对仓库里唯一的 .g79_slow.log，发现那是修复前的 FAILED (failures=1, errors=1)。正确做法是把命令 + 输出尾部写进版本控制里的 docs/验证记录-*.md 或 evidence/*.json（决策 D31），*.log 只能是过程物。
  8. SSE 这一项本轮验证了哪四件事？
    答：①/api/events 返回 text/event-stream 且有 retry: 帧；②进程内 event_bus.publish 的事件真的流到 HTTP 客户端；③入总线前已打码（token 与 URL 内嵌凭据都取不到）；④非回环绑定被拒绝、关闭后端口释放。另加验证了 /api/events/snapshot。
  9. 为什么这轮不删根目录那 24 个 .log？
    答：它们是各次「红→绿」的唯一本地物证（例如上面那次 FAILED 原文），且全部被 .gitignore 覆盖、不进仓库、不影响干净检出。清理前应先在受控位置留快照，否则会重演「结论没留证据」的老问题。
  10. 如果要把主窗 __init__（233 行）拆小，需要先做什么？
    答：先写 AST 行数守卫（__init__ ≤60 行）并让它能失败，再「只搬语句不改语义」地抽私有方法，薄方法保留；随后跑定向回归（test_g52_mainwindow_extra / test_g66_patch / test_g68_settings_ui）+ 截图 38/38 + 打包 E2E。属 v9.11 的 T-41/T-42。

挂机收菜轮变更报告 — Rev22 发布后深审计第二轮 + Qt 消息归档

2026-11-26 · 基线 v9.24.2（HEAD efc4155）· 本轮 2 个生产修复随下个版本发版 · 证据标签：已验证（本轮实际运行）/ 静态确认（读代码）· 原始证据 evidence/rev23-harvest.json

1. 为什么做这次变更

用户以「挂机收菜模式」终极提示词要求补齐上一轮（Rev22 发布后补审计）显式跳过的项目：覆盖率口径实测、HTML 变更报告+测验、第二轮 Agent 管理 Agent 外部扫描、独立对抗审查。对发布后唯一生产代码变更 gcm/app/exc_dump.py 做对抗审查时抓到两个真问题：

  • SystemExit 语义错误：线程 hook 会把正常线程退出的 SystemExit 记成「未捕获异常」写进 error.log — 违背 CPython 官方「silently ignored」语义，给 0xC0000409 排查制造假错误噪音。
  • 文档谎：模块顶部 docstring 声称「Qt qInstallMessageHandler：Qt 层致命/警告也归档」，但全库代码从未安装该 handler（外部扫描 Q1 交叉确认）。而 qFatal 在 abort 前的「遗言」正是两次闪退（0xC0000409）排查都缺的证据面。

2. 关键决策与取舍

决策取舍与理由
修 SystemExit（短路跳过）而非记录它CPython 文档语义是静默忽略；error.log 是错误面，正常退出写进去就是假错误——正是闪退排查最怕的噪音。5 行短路 + 子进程负向守卫（正常退出不得留痕）。
文档谎选择「补齐能力」而非「删承诺」Qt 消息（尤其 qFatal 遗言）是真实观测缺口；实现约 40 行，且用注入式设计（Qt 顶层函数由 __main__ 传入）不破坏 G80「gcm/app 不 import Qt」冻结边界。
控制台与文件同文案打码「出站即打码」纪律；Qt 消息天然带用户路径。handler 向 stderr 双写保留开发可见性，但内容是脱敏后的同一行。
覆盖率必须用快集口径重测发版放行证据（2444 例）早于两个提交；项目门禁定义即快集口径（Windows 81 / POSIX 80）。第三次快集 2451 例 / 81%，红→绿全过程留档。
HTML 报告走 reports/ 已跟踪惯例目录目录内已有 15 份 change-report 先例（tracked），与 Rev22 轮 change-report-20261126.html 并列。

6. 风险与回滚

  • 行为变化：error.log 新增 qt[LEVEL] 行；线程内 SystemExit 不再留痕（回归 CPython 语义）。
  • 控制台行为：开发控制台里 Qt 警告改由本 handler 输出（同内容、已打码），不再是 Qt 默认格式。
  • 回滚：git revert 本轮提交即可（两处生产代码 + 测试 + 2 条 changelog 碎片）；无数据/配置迁移；碎片未聚合进版本前 revert 无历史负担。
  • 观察点：qFatal 场景下 error.log 的增量（预期极低频）；qt[WARN] 若在用户机器刷屏，按需加节流（当前不加，避免防御性脚手架）。

7. 已知限制

  • 真机触摸屏/读屏器/多显示器仍为开放 beads（13k/cuz），非发布阻塞。
  • qFatal → 0xC0000409 的退出码归因需本机 5 行 abort() 程序实测，本轮未做（外部扫描明确标「未确认」）。
  • S1 SignPath 资格判定与 R1 Immutable Releases 开关属用户账号/仓库动作（已建 beads q0j/b1j）。
  • slow 集与全量 discover 未重跑：本轮变更集中在 app 观测层与入口，快集已覆盖全部触碰模块；push 后 CI 三平台做最终确认。

8. 测验（自测记录）

  1. （判断）线程内 SystemExit 现在会写进 error.log。
    答：错。按 CPython 官方语义静默忽略；修复前会把正常退出误记成未捕获异常。
  2. （选择）qFatal 的「遗言」为什么能留存？
    A. handler 内重抛 B. Qt 文档语义：handler 返回后才 abort，我们在 handler 里先落盘 C. qFatal 不 abort D. 依赖 WER LocalDumps
    答：B。子进程守卫实测：进程异常终止且日志已含 boom-fatal。
  3. （判断）gcm/app/exc_dump.py 直接 import 了 PyQt6。
    答：错。注入式：Qt 顶层函数由 __main__ 传入；G80 边界守卫（test_g80_boundaries）在跑。
  4. （选择）第二次快集红在哪？
    A. UI 截图 B. vulture 死参数 + test_main fake 缺符号 C. 覆盖率低于门禁 D. 网络超时
    答：B。两次红均为本轮自查引入（死参数、fake 未同步新符号），当轮修复，第三次全绿。
  5. （简答）为什么控制台双写也要打码？
    答：出站即打码纪律；Qt 消息天然带用户路径/凭据，stderr 与文件输出同一份脱敏文本。
  6. （判断）覆盖率门禁口径是「全量 discover 用例的 80%」。
    答：错。快集口径，Windows 81 / POSIX 80；本轮 81%（21580 stmts）。
  7. （简答）本轮外部扫描哪条被直接采纳落地？为什么？
    答：Q1 Qt 消息归档：文档谎必须闭环；qFatal 遗言补上 0xC0000409 最缺的证据面；注入式实现 40 行内且不破边界。
  8. （简答）回滚本轮修复的方式？
    答：git revert 对应提交（exc_dump / __main__ / 两个测试文件 / 2 条 changelog 碎片），无数据与配置迁移。
  9. （判断）38 张截图审计等价于真机交互验收。
    答：错。离屏渲染验证布局与渲染路径；真机点击/读屏器/触摸在 beads 13k/cuz。

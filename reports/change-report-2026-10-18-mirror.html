镜像多备援 · v9.5.0

Git-clone-Max · 2026-10-18 · G58-2
需求：网络不好的时候，默认走国内镜像；镜像没有这个仓库，就用源站重试。

结果：内置 4 个用 git 实测过的国内镜像，克隆前逐个探测、取最快可用者； 镜像不可用或没有该仓库时自动回退源站；更新失败也能在镜像/源站之间切换。 有令牌时绝不走镜像，避免凭据泄漏给第三方。

一、为什么不能用 HTTP HEAD 测镜像

实测结果直接推翻了这个直觉：

镜像HEADgit ls-remote结论
gh.llkk.cc403✅HEAD 不可信
ghfast.top403✅HEAD 不可信
ghproxy.net403✅HEAD 不可信
ghproxy.com200❌ 302HEAD 假阳性
mirror.ghproxy.comTLS EOF❌不可用
唯一可信的判据是 git 自己能不能连上。
所以探测固定用 git -c credential.helper= ls-remote --exit-code <url> HEAD： 不弹凭据框、不读钥匙串，退出码 2（空仓库）也算可达。

二、内置镜像（实测中位延迟）

顺序镜像延迟
1https://gh.llkk.cc~2.4s
2https://gh-proxy.com~3.3s
3https://ghfast.top~3.6s
4https://ghproxy.net~8.0s

预设是第三方服务，会失效。设置页可关闭，或点「测速并排序」按当前网络重排。

三、失败链（克隆）

候选镜像（用户配置优先 → 内置预设）
  └─ git ls-remote 探测（8s 超时）
       ├─ 可用 → 用这个镜像 clone
       │     └─ clone 仍失败 → 回退源站重试一次
       └─ 不可用/没有该仓库 → 下一个镜像
             └─ 全部失败 → 源站（保证不会因为镜像挂了而失败）

四、更新也会回退

git fetch origin（镜像）
  ├─ 成功 → 保持 origin
  └─ 失败 → 依次 set-url 到其它镜像 / 源站重试
        ├─ 成功 → origin 留在可用地址
        └─ 全失败 → 恢复原 origin，如实报错

五、安全边界（硬约束）

场景行为原因
配置了 token / host_tokens绝不走镜像 第三方镜像能看到 Authorization 头
SSH / 本地路径不拼接 前缀代理只对 HTTPS 有效
镜像全挂回退源站 源站永远是最后候选

六、真实端到端（本机实测）

① 镜像克隆（默认预设）      → SUCCESS · 6.3s · 使用镜像（2940ms）：gh.llkk.cc
② 镜像不可达 → 回退源站      → SUCCESS · 6.7s
③ 镜像克隆后增量更新          → SUCCESS · 4.8s · 已是最新
④ 更新时镜像失效 → 自动切换   → SUCCESS · 8.7s · set-url 到 gh.llkk.cc
